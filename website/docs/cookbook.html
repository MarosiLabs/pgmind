Manual / Cookbook

Cookbook

Recipes for the things people actually ask pgmind to do: keep several agents writing to one note without losing edits, walk the link graph, retrieve without embeddings, cite a paragraph and resolve the citation later, isolate tenants, erase a person, and survive the traps.

How to read this page

Every block below was executed, in this order, against a database seeded with the seven-note demo vault, and the output is what psql printed. The page therefore has a plot: recipes change the vault, and later outputs reflect earlier edits. UUIDs are yours to differ on. Where a block is illustrative rather than executed — the two client-library examples and the backup checklist — it says so.

Two conventions that will save you an afternoon

The six block-level write operations return a composite, so they are always called from FROM, never from the select list — SELECT (knowledge.update_block(…)).* applies the edit once per output column. It is measured in the sharp edges. And several recipes read pgmind.* tables directly: that is admin reach (Admin, Law 11 in the handbook), it is not covered by any stability promise, and it is flagged where it happens.

Agent memory

Several processes, one vault, no lost writes. Everything here is the public knowledge API; nothing needs a lock you take yourself.

Append a line under a heading

Problem. An agent has one fact to record and does not want to read, rewrite and re-check a whole note to do it.

append_to_section resolves the heading, takes the note's row lock, and splices after the last anchorable block in that section, so no caller ever sends the whole document. Two blocks came back for one bullet because a list item and its inner paragraph are separate rows — see the block taxonomy and the reference entry.

CREATE SCHEMA IF NOT EXISTS app;

CREATE FUNCTION app.append_line(p_path text, p_line text, p_tries int DEFAULT 5)
RETURNS uuid LANGUAGE plpgsql AS $body$
DECLARE
  v_head uuid;
  v_doc  text;
BEGIN
  FOR i IN 1..p_tries LOOP
    SELECT head_revision, knowledge.read(path) INTO v_head, v_doc
      FROM knowledge.notes(p_path);
    BEGIN
      RETURN knowledge.write(p_path, (v_doc || p_line || E'\n')::markdown,
                             expected_head => v_head);
    EXCEPTION WHEN sqlstate 'PM009' THEN
      PERFORM pg_sleep(0.02 * i);   -- somebody else won; re-read and try again
    END;
  END LOOP;
  RAISE EXCEPTION 'pgmind: gave up after % attempts on %', p_tries, p_path;
END;
$body$;

NOTE = "daily/2026-08-06"

with psycopg.connect("dbname=vault") as conn, conn.cursor() as cur:
    # Bind markdown as an ordinary text parameter and cast in SQL. Never
    # interpolate it: the markdown type has nothing special at the protocol
    # level, and a note full of quotes will find any hole you leave.
    cur.execute(
        "SELECT revision FROM knowledge.append_to_section(%s, %s, %s::markdown)",
        (NOTE, ["2026-08-06", "Log"], LINE),
    )
    revision = cur.fetchone()[0]

    # A whole-note rewrite, guarded. PM009 means somebody else got there
    # first: re-read and re-apply, do not force.
    cur.execute("SELECT knowledge.read(%s)", (NOTE,))
    doc = cur.fetchone()[0] + "\n- 09:21 window closed\n"
    try:
        cur.execute(
            "SELECT knowledge.write(%s, %s::markdown, expected_head => %s)",
            (NOTE, doc, revision),
        )
    except psycopg.errors.Error as e:
        if e.sqlstate == "PM009":
            conn.rollback()          # caller retries the read-modify-write
        else:
            raise                    # e.diag.message_detail names the value
    conn.commit()

A Python list binds to text[], which is what heading_path wants; the ::markdown cast happens server-side so the driver never needs to know the type. e.sqlstate carries the PM code verbatim — that is the whole point of a custom SQLSTATE class. See the error table.

node-postgres, same shape

Problem. Call pgmind from Node with the same guarantees.

import { Pool } from 'pg';

const pool = new Pool({ database: 'vault' });
const md = '- 09:20 rotation window reviewed\n';

const client = await pool.connect();
try {
  await client.query('BEGIN');
  // SET LOCAL keeps the tenant inside this transaction, which is what
  // makes the recipe pool-safe.
  await client.query('SET LOCAL pgmind.vault_id = $1', [tenantId]);

  const { rows } = await client.query(
    `SELECT revision, block_ids
       FROM knowledge.append_to_section($1, $2, $3::markdown)`,
    ['daily/2026-08-06', ['2026-08-06', 'Log'], md],
  );

  await client.query('COMMIT');
  return rows[0];
} catch (err) {
  await client.query('ROLLBACK');
  if (err.code === 'PM009' || err.code === 'PM016') {
    return null;                 // caller re-reads and retries
  }
  throw err;                     // err.detail carries the offending value
} finally {
  client.release();
}

err.code is the SQLSTATE and err.detail is the DETAIL: line, which always names the offending value — the head that was expected, the hash that was current. A JavaScript array binds to text[] the same way psycopg's list does.
