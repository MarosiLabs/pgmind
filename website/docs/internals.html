Internals

How pgmind stores a vault, how a write becomes rows, how identity survives an edit, what history costs, what two writers do to each other, and what happens when you have to erase something. This page is for deciding whether to trust it, so every non-obvious claim names the file or the RFC decision it comes from.

How to read the citations

extension/src/write.rs:899 is a line in this repository at the commit this manual was written against; line numbers drift, the function names do not. RFC-005 D5.2 is a numbered decision in an accepted RFC. Where an RFC and the code disagree, this page documents the code and says that it does.

What this page shows you

Several examples below read and write pgmind.* tables directly. That is admin reach — Law 11 permits it for debugging and operations, and forbids building on it. Direct DML into pgmind.* bypasses every maintenance path on this page and is unsupported; pgmind.verify_note() exists to detect it. Everything an application should depend on lives in knowledge.*.

The eleven laws

The handbook §6.2 states eleven architecture laws — constraints, not preferences. An RFC that violates one has to say so in its title. Most of the design decisions further down this page are downstream of one of them, so here they are with the thing each one forbids, which is the part that actually binds.

LawWhat it forbids
1. AI-free core Any model invocation anywhere in the extension or the tools. No embedding is computed here, no summary, no extraction. External enrichment gets hook tables, not a home.
2. No synchronous network I/O Opening a socket inside a transaction or an API call — including to resolve a link, check a URL, or call an embedding service on write.
3. Markdown is a boundary Storing a parsed AST as the system of record. The record is per-block relational rows; the AST is transient.
4. Parsing yields structure, not identity Deriving a block's id from its content. The parser produces kinds, hashes and positions; the write path mints identity.
5. IDs and hashes are different things Collapsing the two. The id answers "same block"; the hash answers "same bytes", and it is what lets an embedding pipeline skip an unchanged block.
6. Compose with incumbents A bespoke vector index or search engine inside pgmind. pgvector and PostgreSQL FTS already exist.
7. Incremental maintenance only Any operation that rebuilds the link graph or the tag index for the whole vault. Edits update from block diffs.
8. Append-only with audited excision An unlogged deletion of history, and any background job that deletes when nobody is watching.
9. Feel like PostgreSQL — and like a vault Triggers, rules and hidden behaviour; ontology jargon where "note", "link" and "tag" would do.
10. context() is a mode, not a monopoly A planner primitive reachable only through the one big function. Phase 5
11. Layers by contract, not by wall A public API depending on undocumented internals — and an admin/debug interface that reaches deeper without being marked as one. That is why the pgmind schema exists and why this page labels it.

Two lanes

A note is stored twice, in two lanes that answer different questions (RFC-003 D2).

  • The byte lane is note.preamble plus an ordered array of tile rows. A tile is one top-level child of the document — a heading, a paragraph, an entire list, an entire table. Concatenating the preamble and the tiles in ord order reproduces the source byte for byte. That concatenation is the source_of() invariant (extension/src/store.rs:220), and it is what knowledge.read() returns.
  • The semantic lane is one block row per addressable block, with its kind, normalised content, BLAKE3 content hash, heading_path, parent, and its position expressed relative to its tile (tile_ord, start_in_tile, end_in_tile).

Tile-relative spans are the reason an edit is cheap: editing one paragraph rewrites one tile's bytes and leaves every other tile's stored text — and every other block's stored span — untouched. Absolute offsets would make every block after an edit dirty.

There is a third lane in the schema, and it is deliberately not part of this pair: history stores pre-images, in its own tables, and current state never reads them. A note at head costs exactly what it would cost with no versioning at all — the head read in the published capacity run is 0.33 ms p95 whether the note has one revision or twenty-five. excision_replay The executable erasure target — which for the literal and path forms is the identifying data. The one table not registered for dump, and the sweep's one named exception.

Indexes

Twenty-four CREATE INDEX statements, all in the install script from schema.rs:248 onward, none added by a migration afterwards. (The indexes column above counts more, because it also sees primary keys and unique constraints.) The ones worth knowing about:

  • note_live_path is UNIQUE (vault_id, path) WHERE tombstoned_at IS NULL — a partial unique index, so a tombstone does not block re-creating the path, and undelete_note has to check occupancy itself (PM015).
  • note_basename and note_path_prefix (text_pattern_ops) serve the two halves of link resolution and glob prefix pushdown.
  • block_note_hash on (note_id, content_hash) is what makes the carry's pass-2 lookup a probe rather than a scan.
  • tag_lookup is on (vault_id, lower(tag)) — tags group case-insensitively, so the index has to as well.
  • block_vault, revision_vault and tile_vault exist because vault_id is the predicate on every knowledge.stats() count and on the RLS policy. Without them stats() sequentially scans three heaps.
  • revision_parent was deferred by RFC-003 D4 by name and added by RFC-005: Phase 2 had no deletion path, Phase 3 has several.

Three deliberate omissions

  1. No foreign key on note.head_revision (schema.rs:59). A circular note↔revision FK makes pg_dump warn and makes a plain-psql restore impossible. The constraint is real; it is enforced by pgmind.verify_note() instead of by the catalog, which is a trade the RFC states rather than hides.
  2. NO ACTION, not CASCADE, on block.parent_block (schema.rs:106). A wrong reconcile order then fails loudly instead of quietly cascading away carried children. The write path's INSERT/UPDATE-before-DELETE rule (step 11) is what keeps it from firing.
  3. No partitioning. RFC-005 D9 tested it and refused it for v1: extension-script partitions vanish from pg_dump entirely; a partitioned index on an extension-owned parent breaks plain psql restore; and RLS on a partitioned parent is bypassed by selecting from a leaf. Retention is therefore DELETE-based, with the honest consequence that deleted history returns space to the heap for reuse, not to the operating system.

lz4 TOAST compression is requested for the ten large text columns inside a DO block that catches feature_not_supported and warns. On a server without lz4 you get WARNING: pgmind: lz4 toast compression unavailable on this server at CREATE EXTENSION. It is a warning, not an error, and everything works without it.

The write path, step by step

knowledge.write() is write_note() in extension/src/write.rs:899. It is one function, no triggers, no rules, and the order of its steps is normative — several of them are in that position because putting them anywhere else produced a bug that was found the hard way. Each step below says why it sits where it sits.

  1. Normalise and validate the path. NFC-normalise, trim, then check the grammar; PM001 on failure. Normalisation comes first because macOS hands out NFD and a reader that skipped this could not find a note it had just written (store.rs:134).

  2. Take the advisory lock on (vault, path) (store.rs:665). This is the name lock, and it is a different domain from the row lock in step 4. Without it, two sessions racing to create the same path get a bare 23505 out of note_live_path — an error the caller cannot act on and which RFC-005 D5.8 promises never to raise.

  3. Look up the live note by path. Tombstones are filtered out, so a path whose only note is deleted looks like a path with no note.

  4. Take FOR NO KEY UPDATE on the note row (store.rs:581). Not an advisory lock: this one blocks writers without blocking readers, is released by the transaction, and shows up in pg_blocking_pids() — which is what lets the concurrency gate test interleavings without sleeping. It is taken with Spi::connect_mut and update, because pgrx runs SPI read-only while the transaction has no XID and FOR NO KEY UPDATE in a read-only context is rejected outright (25006) — which is exactly the first mutating operation in a transaction.

  5. Re-read path and head_revision from under the lock, and raise PM002 if the path changed. RFC-005 D5.2a is normative here and was amended after acceptance: the note row lock protects the note row and nothing else. Holding it does not stop another session inserting that note's tiles or updating its blocks. So every value the operation depends on — both lanes' pre-image, the head, the path, the floor — must be read after the lock, or the writer computes a pre-image from a state its own lock never covered.

  6. Compare-and-swap (store.rs:616). If expected_head is non-NULL and differs from what step 5 read, raise PM009. If the path had no live note and expected_head was given, raise PM009 too — a caller that asserted a head is editing something, and answering with a silent create makes its CAS unenforceable exactly when it matters, which is while racing a concurrent delete (RFC-005 D5.6).

  7. Then the byte-identical short-circuit (write.rs:946): if preamble ‖ tiles equals the incoming source, return the current head and write no revision at all. The order of 6 and 7 is the load-bearing part. The short-circuit answers "did anything change"; CAS answers "did you see what you were changing". Reordering them lets a stale writer's byte-identical no-op succeed silently (RFC-005 D5.5).

  8. Parse — once, with the only parser (pgmind-core), over the whole document. SQL never re-implements it, and no read path ever re-parses.

  9. Run the identity carry (next section): each parsed block gets a carried or a freshly minted UUID.

  10. Capture the pre-image (history.rs:122), before anything is mutated. This is the whole reason the step exists at this position: after reconcile runs, the bytes the pre-image records are gone. RFC-005 D4 is one sentence — "before mutating a lane, record its pre-image" — and it is the only ordering rule the history engine has.

  11. Reconcile the lanes by set-diff (write.rs:506), in this order: (a) the note row's preamble and properties, guarded so an unchanged note writes nothing; (b) tiles, by set-diff on (ord, raw) — an unchanged tile emits no SQL at all, which is the property Law 7 depends on; (c) INSERT minted blocks and UPDATE carried ones whose stored columns actually changed; (d) DELETE removed rows last (write.rs:699). The INSERT/UPDATE-before-DELETE order is normative: carried children are re-parented before any parent row can disappear, and the NO ACTION FK turns a violation into a loud error rather than a silent cascade.

    Each lane flushes in chunks of 2048 rows (write.rs:446). That bound is not cosmetic: jsonb caps a single string, and an array's element total, at 256 MB−1, where a text datum caps at 1 GB — so an unbounded batch would have rejected documents the per-row implementation stored. Unbounded columns therefore travel as text[], joined on ordinality, and never inside the jsonb. Chunking also makes parse order load-bearing: a non-deferrable FK is checked at the end of each statement, so a minted child must not land in an earlier chunk than its minted parent. doc.blocks is pre-order, so this holds by construction.

  12. Reconcile extraction — edges and tags — by set-diff on natural keys, against the full new parse, never per changed block (write.rs:714). CommonMark makes extraction document-global: adding a [foo]: url reference definition in one paragraph changes whether [[foo]] elsewhere is a wiki-link at all. Set-diff gives Law 7's no-rebuild property without pretending extraction is block-local. Every distinct new target is resolved in one pass (store.rs:348), two queries total rather than a round trip per link.

  13. Insert the revision row and swap the head (write.rs:396), then write the H1/H2 history rows (history.rs:256) and, when seq lands on the cadence, an H3 frame (history.rs:376). H1 has a foreign key to revision, so this has to follow the revision insert and not precede it.

  14. Repair other notes' edges — last, and only on creation (store.rs:431). A new path can promote a dangling edge to resolved, or a basename match to exact, anywhere in the vault. It runs last because it is the only step that touches rows belonging to other notes, and it takes their row locks in ascending note.id order before doing so (see below).

The deterministic carry

Rewriting a whole note must not renumber it. RFC-004 A3 defines three passes; write.rs:164 is the single normative implementation, shared by knowledge.write() and by the five block operations (it used to exist twice, and the copies had already drifted on whether an already-claimed holder stays claimable).

  1. Pass 1 — ^id claims. Per marker value, only the lowest-ord unused old holder is claimable, and only the lowest-ord new claimant wins; duplicates on either side behave as unmarked and fall through to pass 2. A marker is an explicit assertion by the author, so it outranks content.

  2. Pass 2 — exact content match, in two tiers. Blocks are paired k-th↔k-th in document order by content hash. Tier 0 requires the same heading_path; tier 1 drops it.

    The tiering is not an optimisation, it is a correctness fix. The content hash covers (kind, normalised content) and not heading_path. With a single untiered pass, deleting a section handed its paragraph's id to an identical paragraph in a surviving section while the survivor's own id was deleted — an id silently changing what it points at, which RFC-004 A1 forbids. Tier 1 still lets a renamed heading carry its whole section's blocks, which is the case people actually hit.

  3. Pass 3 — mint and remove. Anything no pass claimed mints a fresh UUIDv7; any old block nothing claimed is removed (write.rs:241). Heuristic rebinding runs between passes 2 and 3, and only for knowledge.write().

Heuristic rebinding

Deterministic carry stops where the bytes stop matching. An agent that reads a note, paraphrases a sentence and writes the whole thing back has changed the hash of every block it touched, and RFC-004 Part B is the layer that tries to keep those blocks' identities anyway (extension/src/rebind.rs).

Where it runs, and where it does not

Between passes 2 and 3, on the knowledge.write() path only (write.rs:296). The five block operations call carry_scope directly and never reach it: they carry explicit intent, and guessing for a caller who said what it meant is strictly worse than obeying it. Nothing it infers is stored as though it were certain — every inferred binding writes block_revision.confidence, and a deterministic one leaves it NULL (Law 8, RFC-005 H2).

The mechanism

  • Features (rebind.rs:57): token unigrams ∪ bigrams, lowercased, FNV-1a hashed, sorted. The draft said "token-bigram Dice"; bigrams alone are unusable at the short end, because a one-word fragment has none and therefore shares nothing with anything. Unigrams put short and long content on one scale; bigrams keep word order mattering. Sorted u64 rather than a map of strings, so multiset intersection is a linear merge with no allocation per comparison — which is what makes an O(n·m) loop affordable at all.
  • Similarity (rebind.rs:101): Dice over the feature multisets.
  • Splits (rebind.rs:148): a split run is 2 to MAX_RUN = 4 consecutive same-kind peers — consecutive among peers, not adjacent by ord, because a list item is a list_item block plus the paragraph inside it, so two sibling items' fragments are never adjacent on either stricter reading. Both stricter readings silently never fire on lists.
  • Containment, in both directions (rebind.rs:111). The run must cover the original, and every fragment in it must itself be made of the original. One direction is not enough: a moved-and-edited paragraph is "covered" by the run {unrelated new paragraph, the moved one}, so a one-way rule calls that a split and hands the id to a block the author had never written.
  • Alignment (rebind.rs:176): maximum-weight order-monotonic matching by dynamic programming. The RFC says no crossing matches and does not say how ties resolve; maximising total score is the reading that does not depend on iteration order. Monotonicity is enforced within the residual only — extending it to bindings the deterministic passes already made was measured and refused (B5): it buys precision 0.969 → 0.989 and costs four inferred bindings, every one of them a move. A rebinder that cannot follow a block across a document is refusing the case it is most needed for.
ConstantValueWhy that value
TAU0.5 Measured, not chosen: recall on the corpus's inferred class is flat for every τ ≤ 0.5 and falls above it, so this is the highest threshold that still reaches maximum recall.
TAU_SPLIT0.6 Does not discriminate — every value from 0.3 to 0.9 gives an identical corpus result, because what decides a split is the two-way test, not where its threshold sits. Kept as a named constant rather than advertised as a tunable nothing constrains.
MAX_RUN4 Beyond four consecutive fragments the scan cost grows without the corpus showing anything to find.
CELL_BUDGET40 000 The O(n·m) alignment runs on the write path inside the transaction, so it gets a ceiling. Over it, the whole heuristic is skipped, every unmatched block mints, and the revision records meta.rebind = {"skipped":"budget", …} — a skipped note churned identity silently otherwise, and silently is the part worth fixing. The residual is unmatched blocks only, so an ordinary edit is orders of magnitude below it; what blows it is a large document rewritten wholesale, where carrying nothing is the right answer.

The cases it will not solve

Five of the 101 expected bindings are missed, four of them in the inferred class, which carries 19 of its 23 — that four is the figure RFC-004 B5 quotes, not the total. Lowering τ does not recover them. Two are edit-in-place: a heading that gains two words, and a two-word block with one word changed. At that length token bigrams carry almost no signal, and a τ loose enough to catch them starts accepting noise. One is a move-edit where two blocks swap and both are edited — any binding there is a crossing match, and an order-monotonic aligner has to drop one of the two. The last two are a single near-duplicate case: two byte-identical paragraphs, the first of them edited, so the survivor's hash matches both originals and k-th ↔ k-th pairs it with the wrong one. That one case also produces both false positives. If identity across an edit like that matters to you, put a ^id marker on the block: pass 1 is deterministic and no heuristic ever overrides it.

Block-operation mechanics

The five block operations — insert_blocks, update_block, move_block, split_block, merge_blocks, plus append_to_section which delegates to the first — edit bytes surgically instead of rewriting the note. They all share commit_op() (extension/src/ops.rs:369), and they all end at the same reconcile and the same history recorder as write(), so history cannot drift between the two write paths.

Splice, separator synthesis, and the PM008 assertion

An operation locates its target's byte range, splices the replacement in, and then re-parses the whole reassembled note. Tile-local re-parsing is unsound and was verified to be: an unclosed fence or a type-1 HTML block in a fragment swallows every following tile, and a spliced paragraph can be absorbed backward by a preceding construct.

Newly written interior lines take canonical decoration — quote prefix "> ", item continuation as marker-width spaces, fragment list markers restyled to the destination list's marker and numbering. Bytes outside the spliced span are never reformatted, and the replacement carries exactly the terminator the replaced region carried, which everywhere but the end of a note is a newline.

Separator synthesis is scoped to the seam (ops.rs:1417) — the inserted or relocated tile run plus the tile immediately before it. Applying it to every tile rewrote bytes far outside the splice: para\n# Heading\n is legitimately two tiles with no blank line between them, and any later insert silently rewrote them to para\n\n# Heading\n\n. PM008 cannot catch that, because RFC-002 D7 strips trailing newline runs before hashing, so every outside block's kind and hash are unchanged. Scoping to the seam is what the no-reformat rule always required.

Then the assertion. After the re-parse, the block multiset outside the spliced region must be unchanged — same count, same kinds, same hashes, in order. Anything else is PM008 and the operation aborts rather than silently retiring a neighbour's identity:

psql
-- replacing a paragraph with an unclosed fence would swallow the rest of the note
SELECT knowledge.update_block(
  (SELECT block_id FROM knowledge.blocks('projects/auth') WHERE content LIKE 'The service%'),
  $md$```$md$);
ERROR:  pgmind: splice restructures adjacent content
DETAIL:  pgmind_splice_restructures — 14 blocks outside the edit before, 1 after

move_block is the case that makes this rule subtle: it rewrites the whole note and pins every block by permutation, so its outside set is empty and the comparison would be 0-against-0 — asserting nothing, and letting a re-parse that produced extra blocks mint fresh ids in silence. When there is no outside set the assertion is made directly instead: the block count must be unchanged and every new block must be covered by a pin (ops.rs:423 and ops.rs:434). The RFC states the general form of the lesson — implementations must not encode "this check does not apply here" as a sentinel whose emptiness depends on downstream arithmetic.

Anchors, containers, markers

  • Anchor legality. insert_blocks anchors on a top-level block or a list item, and nothing else. "Top level" is a property of the parse, not of the stored row (ops.rs:1319): a paragraph inside a top-level blockquote has parent = NULL and starts at the tile boundary, and matching on either alone accepted it — which let an insert splice a new tile outside the quote without the PM005 the guard exists to raise. The block must span the whole tile.
  • Container constraints (v1). A target whose own content is non-contiguous — content after a container child — is PM006. A replacement fragment must not itself contain nested containers, and a target that has container children must be replaced by something that stays a list item. move_block reorders siblings within one container or at top level; cross-container moves are PM006.
  • Item re-marking. Fragment list items are re-marked to the destination list's style — marker character for unordered lists, delimiter for ordered ones, with the numbers kept.
  • ^id markers survive splits and merges. marker_holder (ops.rs:645) scans each candidate's whole subtree, because on a list item the marker rides on the item's inner paragraph; scanning only the roots reported "no holder" for markers that plainly survived. The surviving block is named by uuid in revision.meta, resolved after the carry because identities do not exist before it.
  • Only update_block takes expected_hash. Split, merge, move and insert address blocks too and could take the same guard; nothing has asked for it, and widening later is additive where narrowing is not.

The history engine

Versioning is where a design usually starts taxing the present to pay for the past. pgmind's does not, because it stores the past as pre-images.

Pre-images, not post-images

A post-image ledger records what each revision produced: current state is then the sum of the chain, and reading a note at head means replaying it or maintaining a separate materialised copy. A pre-image ledger records what each revision replaced. Current state stays plain current state — the same note, tile and block rows a version-less design would have — and reconstruction runs backwards from an anchor at or above the target (extension/src/history.rs, timetravel.rs:305).

The consequence is the one that matters in production: a read at head pays nothing for history at all, and history's cost is proportional to what changed rather than to what exists.

X1 and X2, and what each buys

InvariantStatementWhat it buys
X1 No history row defines its bytes by reference to another history row's bytes. Every payload is literal. Erasure is a bounded local rewrite. With delta chains, erasing one revision's content re-bases every successor; with literal payloads, excision is an UPDATE of the rows that hold the text and nothing else. This costs storage — deliberately, and the measured price is 0.207× current state.
X2 Reconstruction never invokes the parser. Structure at a past revision comes from stored vectors. History survives a parser change. An amendment to the markdown dialect cannot silently re-interpret what an agent read last month, and a revision cannot depend on the block taxonomy of the current build. It also means a frame has to snapshot both lanes, since recovering the semantic lane by re-parsing the frame's bytes is exactly what X2 forbids.

The KEEP/INS script

Two vectors — the tile array and the block-id array — are diffed against their newer selves and stored as a script that rebuilds the older from the newer (history.rs:45). KEEP start len copies a run from the newer vector; INS count takes the next count elements from a literal payload (that is X1). The diff is common prefix + common suffix, deliberately not an LCS: a minimal edit script costs O(n·m) on a lane that a whole-document rewrite touches entirely, and the payoff is only in the multi-site-edit case. Prefix/suffix is O(n), exact for the single-region edits that dominate, and degrades to "store the changed middle literally" otherwise — correct, only larger.

Positional facts vs content-visible ones

This is the single most consequential rule in the design's economics (RFC-005 D4). A block_revision row is written only when a content-visible column changed: kind, content, content_hash, block_ref_id, attrs, parent_block. Five columns never produce one — ord, tile_ord, start_in_tile, end_in_tile and heading_path. They ride the per-revision vectors in note_revision instead, as changed slots only.

Without that rule, inserting a block at the top of a 100-block note writes 100 full history rows for an edit whose semantic content is one block. And structural churn is exactly the workload an importer produces, so a design that is O(note) per structural edit fails on the traffic it was built for.

heading_path is the interesting member of that list, and it was moved there after RFC-005 was accepted. It had been classified as content-visible — and the same paragraph offered "renaming a heading" as the case the rule saved, which it did not: a rename changes no ord at all, but rewrites heading_path for every block in the section. Renaming a ## heading above 60 blocks wrote 60 full effect rows. heading_path is derived from the preceding headings (RFC-002 D6), which makes it a positional fact, so it belongs with the others; head_idx/head_prev carry the changed slots. The carry example above is that exact case, costing two rows instead of two plus one per block in the renamed section.

The reconstruction algorithm

  1. Resolve the target to a (note, seq) (timetravel.rs:113). A revision id that is not this note's is PM010; a seq below note.history_floor is PM011. Those two mean opposite things to whoever is debugging — "your client is wrong" versus "your operator retained it away" — so they are never interchanged.
  2. Find the nearest anchor at or above the target (timetravel.rs:231): the nearest frame with seq ≥ target, or current state. A frame is only used if it is closer than head.
  3. Read the pre-images of every revision above the target, newest first, in one statement. One statement is not a performance choice. pgrx runs SPI read-only only while the transaction has no XID, so any prior write in the caller's transaction puts each subsequent statement on a fresh snapshot — and a concurrent commit between two of them yields a document one revision off, silently. This was reproduced on PG 18.4; the fix is a single query.
  4. Apply each revision backwards: rebuild the tile and id vectors with the KEEP/INS scripts, restore the note-lane columns that changed, override the named positional slots (everything else inherits by block id from the newer state), then apply the effect rows — existed = false means the block did not exist yet and is dropped; a pre-image means restore it.
  5. Never return a partially reconstructed document. The failure this most wants to prevent is an agent citing a revision and receiving a plausible, wrong one.

Redacted pre-images

A NULL in a prev_* column normally means "this column did not change". Erasure would be indistinguishable from that, which would make redacted history reconstruct as though the erased text had never been edited — so excision sets block_revision.redacted = true, and the reconstructor reports such a block as erased (attrs = {"redacted": true}, empty content) rather than inheriting the newer value. Unknown is reported as unknown, never as a plausible wrong answer.

Concurrency

Everything here is one PostgreSQL transaction. pgmind adds no locks of its own beyond the two below, runs no background worker, and never retries anything for you.

Two lock domains

They protect different things and confusing them produced two separate bugs.

Multi-note operations, and what pgmind never raises

  • Any operation touching more than one note locks in ascending note.id order, so two writers touching the same pair cannot deadlock. This includes edge repair (store.rs:431), which was not treated as a multi-note operation until RFC-005 D5.9: it rewrites other notes' edge rows, and did so while holding only its own note's lock.
  • pgmind.enable_vault_rls() enumerates its tables in pg_class.oid order for the same reason. Each ALTER TABLE takes ACCESS EXCLUSIVE and holds it to commit, so the loop order is a lock order — and creation order is the order every writer touches these tables in. Alphabetical takes block before note and deadlocks against any concurrent write (observed, schema.rs:329).
  • pgmind never raises 40001 or 40P01 itself, and never retries internally. Conflicts it detects are PM0xx with the observed value in the DETAIL, so a client can re-read and retry deterministically. Serialization failures PostgreSQL raises under REPEATABLE READ or SERIALIZABLE pass through untouched — an extension that swallowed them would break your own retry loop.
  • expected_head => NULL is last-writer-wins, explicitly and by the caller's choice.

Erasure and retention

Erasure is the half of Law 8 that a version engine fakes most readily. Four obligations: erase from every surface including derived ones, refuse rather than half-erase, log the erasure, and prove it (extension/src/excision.rs).

If the target is still live at head, pgmind.excise raises PM012. An erasure that quietly left the current copy in place would be the worst possible outcome of a right-to-erasure request. The sweep, and why pg_catalog

Every text-bearing column in schema pgmind is enumerated at call time from pg_class/pg_attribute (excision.rs:23), so a table added by a later RFC is inside the sweep by construction rather than by someone remembering.

It is emphatically not information_schema, whose views are privilege-filtered by the current user. That difference was measured: the same sweep saw 46 columns as the extension owner and 24 as a Law-11 erasure admin granted rights on exactly the history and audit tables — so the live pgmind.block lane was never opened, a canary still sitting in it went unseen, and verify_excision returned a positive attestation of erasure. The anti-vacuity clause, computed from the same filtered view, passed too.

Redaction is a splice, not a NULL

A tile pre-image holds a whole top-level child — an entire list, table or code fence. Nulling it would erase every other block that shared the tile and leave read_as_of reassembling a document with a hole. So the erased span is replaced in place with a marker, ⟨redacted pgmind:‹excision-id›⟩, and redacted history still reconstructs to byte-defined, parseable markdown (excision.rs:415). In the semantic lane the effect row keeps its skeleton — history still knows that a block existed and when — while prev_content, prev_content_hash, prev_attrs and prev_block_ref_id go NULL and redacted goes true. The hash goes too: BLAKE3 of a short block is a confirm-a-guess oracle.

The code disagrees with the RFC here — believe the code

RFC-005 D7.1 says the live-removal step records verb = 'excise'. It does not: the removal is an ordinary audited write through the normal path, so it records verb = 'write' (visible above at seq 1). Two further gaps, stated rather than buried: pgmind.excise and pgmind.verify_excision are specified as SECURITY DEFINER and are not, so today they require a role that can already write the tables; and the shipped verify_excision implements clause (a) of D7.6 — the exhaustive canary sweep — but not the whole-note re-reconstruction of clauses (b)–(d). Escalation to whole-tile redaction and the span-shifting rule are likewise specified and not yet built.

The audit/replay split, and what a restored dump does

Where the target is stored is itself an erasure decision. As RFC-005 was accepted, excision_log.target held the caller's target "as given" and was annotated as carrying no erased content — false for two of the forms, since {"literal":"Jane Doe, 1978-04-02"} is the content and a path like people/jane-doe is identifying data. That table is dump-registered, so it would have become the one copy of the erased string guaranteed to be reproduced in every future backup. Reproduced on PG 18.4: after a maximally thorough excision, the gate's own zero-hit sweep found the canary in excision_log.target and in the raw pg_dump output.

So the log now records only target_kind and counts, and the executable target lives in pgmind.excision_replay, which is not registered for dump and is the sweep's one named exception (named, never silently skipped — a silent exemption is how this check reports green on a broken system).

The honest consequence: restoring a backup taken before an excision resurrects the erased content, and the replay driver that would re-apply it — enforce_excisions() in RFC-005 D7 — is not shipped. Until it is, an operator restoring an old dump has to re-run pgmind.excise by hand. pgmind cannot reach backups it does not know about, and no in-database mechanism can.

Retention

pgmind.retain(keep_revisions, dry_run) raises each note's history_floor to head_seq − keep + 1. It is a function with parameters, not a stored policy catalog: there is no persisted mode that can be toggled into deleting more than the caller asked for, and no background job that runs when nobody is watching. dry_run defaults to true and returns the row count it would remove.

Order inside excision.rs:216 is deliberate:

  1. Write a note_frame at the new floor first — it is the anchor every read at or above the floor depends on, and writing it after the delete would leave a window with no anchor at all.
  2. Delete block_revision, note_revision and every note_frame below the floor. Frames below the floor were not in the deletion set as accepted, so a compacted vault kept full snapshots of exactly the content PM011 claims is no longer reconstructable.
  3. Advance note.history_floor.
  4. pgmind.revision rows are never deleted. A vault that forgot must remember that it forgot: knowledge.history() keeps listing every revision — id, author, source, verb, timestamp — long after its content is gone, with reconstructable = false.

Verification

Three checkers, all admin surface, all returning SETOF text where an empty result means healthy and every row is a specific disagreement.

FunctionWhat it checks
pgmind.verify_note(note_id)
Admin		 Re-parses the note from its own stored bytes and compares everything against the parse (verify.rs:29): head_revision exists and belongs to this note (the FK the schema deliberately omits); preamble length; tile count and bytes; block count, ord density, kind, content, hash, heading_path, block_ref_id, attrs, placement and parent_block; and edges and tags against a fresh recomputation including resolution — RFC-003 D5 says incremental maintenance must be definitionally equal to full recomputation, and this is where that is enforced. It is also the tool that detects direct DML into pgmind.*.
pgmind.verify_history(note_id)
Admin		 Three post-conditions (verify.rs:245). (1) A frame exists at the history floor. (2) seq is dense and gapless above the floor and every revision above it has exactly one note_revision row — the half that catches a history lane which silently stopped being written, including a dump that restored the revisions and lost their pre-images. (3) Reconstruction, checked at the floor, at the newest frame, and at up to 20 deterministically sampled revisions between them; each must yield parseable bytes with an id vector matching the parsed block count and every span inside its tile.
The accepted RFC's post-conditions were all three unsatisfiable, vacuous, or both. The vacuous one is worth naming: read_as_of(head) = read() proves nothing, because reconstruction at head applies no scripts and reads current state by definition.
pgmind.verify_excision(excision)
Admin		 Re-runs the pg_catalog sweep for that excision's target and returns the surviving hits. It also asserts that it looked at something — a sweep that enumerated zero columns would otherwise report success on a broken system. If the replay row is absent (an excision from a restored dump), it says so rather than attesting.

One class of defect verify_note structurally cannot see: operations that append a byte the note never contained. Backup and restore

Tables created by an extension script are skipped by pg_dump unless they are registered with pg_extension_config_dump() (schema.rs:354). Missing one registration loses 100% of that lane from every backup while the rest of a dump-restore test stays green — with block_revision alone unregistered, equal counts across six hardcoded tables, a clean verify_note, and a working post-restore write all pass, and all per-block history is gone. So the check is a run-time enumeration, not a list someone has to remember to update:

Two hazards worth knowing before you need them

  • A newer dump does not restore onto an older build, and it fails partway. pg_dump emits CREATE EXTENSION with no version, so restoring a Phase-3 dump onto a host still packaging Phase 2 installs the old schema and then fails on the first COPY that names a column the old schema lacks (column "history_floor" … does not exist) — after some tables have already loaded. Verified on PG 18.4. Restore onto the same extension build, or newer with a working upgrade script.

  • Restoring an old backup resurrects excised content, and the replay driver that would re-erase it is not shipped. See above.

One feared hazard was tested and refuted: pg_dump orders its COPY statements FK-topologically regardless of registration order, and plain psql -v ON_ERROR_STOP=1 restored all twelve tables cleanly. The comment in schema.rs claiming dump order follows registration order is wrong, and harmless.

The extension is superuser = true, trusted = false, relocatable = false. There is no upgrade path between builds yet; this is research pre-alpha and a schema change today means a rebuild from source.

The AI-free boundary

Law 1 and Law 2 are not aspirations about the roadmap, they are properties of the shipped artifact, and they are checkable from SQL. pgmind invokes no model, opens no socket, registers no background worker, installs no trigger and no event trigger, and needs no entry in shared_preload_libraries.

The 62 are PostgreSQL's own foreign-key enforcement triggers, which every REFERENCES clause creates. Zero are pgmind's. Everything that maintains the link graph, the tag index and the history lanes is an explicit statement on the write path you can read in write.rs, which is what Law 9's "no hidden behavior" means in practice — and what makes pgmind.verify_note() able to say whether the invariants hold, since there is nothing running behind it.

What that buys you, concretely:

  • Allowlisting. The extension is PostgreSQL-licensed, has no runtime dependency beyond PostgreSQL itself, and makes no outbound connection. A security review has a short list to check.
  • Determinism. The same bytes written to the same vault produce the same rows, the same hashes and the same identity decisions, every time. The one heuristic in the system — Part B rebinding — is pure computation over already-loaded rows with a fixed feature function, a fixed threshold and a deterministic tie-break, and it records a confidence for everything it infers. There is no sampling and no clock in it.
  • No hidden cost. Nothing happens between your transactions. There is no autovacuum-adjacent maintenance job, no re-indexing worker, and no retention timer — pgmind.retain only ever runs because you called it.
  • You keep the vector lane. If you want embeddings, you populate your own table keyed by (block_id, content_hash) and pgmind reads it like any other table. The content hash is what lets you skip re-embedding an unchanged block — see the cookbook.

The one place a claim about the writer is not verified is revision.author. It defaults to current_user and can be overridden by the connected role; the value is never validated beyond its length and never namespaced. Any session that can write can claim any author. Dressing that up — a registry, a required prefix, a foreign key to a principals table — would make a claim look verified without verifying it, which is worse than a plain string (write.rs:374). Treat author as an assertion, and put the boundary in grants and pgmind.enable_vault_rls().
