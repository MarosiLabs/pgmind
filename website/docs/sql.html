SQL reference

Everything pgmind 0.0.1 installs: 51 functions across three schemas, four types, four server settings and nineteen error codes. Signatures are copied from pg_get_function_arguments, not from an RFC, so what is written here is what your database will accept.

How to read this page

Every example was executed, in the order it appears, against the seven-note demo vault that Quick start builds. Later examples depend on the state earlier ones left behind, so if you paste from the middle the row counts will differ. UUIDs are elided to their first group (019fd627-…) because yours will differ. Where an example is meant to fail, the real ERROR: and DETAIL: lines are shown.

The vault parameter, once

Every vault-scoped function takes vault text DEFAULT NULL as its last argument. It accepts a vault name or an id in its text spelling; a value that parses as a uuid is looked up by id, otherwise by name. NULL falls back to the pgmind.vault_id setting. An id or name no vault was registered under is PM018 — never an empty result. Passing it per call is what lets one query span several vaults; the setting is the ergonomic choice for a session that stays in one. The per-entry tables below repeat only the default.

Return shape

Six of the seven writing functions return SETOF pgmind.op_result — one row, (revision, block_ids) — every one except knowledge.write, which returns a bare uuid. SELECT * FROM knowledge.update_block(…) is the clearest form, but SELECT (knowledge.update_block(…)).* is now safe too: a set-returning expression is evaluated once. It was not always — while these returned a scalar composite, that idiom applied the edit twice.

Types and values

Four types. One of them, markdown, lives in public so that unqualified literals work; the other three live in pgmind because they are storage vocabulary, not API surface.

markdown In main

CREATE TYPE markdown; -- variable length, in schema public

The boundary type: validated UTF-8 markdown source, stored as the bytes you handed over and never as a parse.

Notes

  • Input is rejected if it is longer than pgmind.max_document_bytes (default 8 MiB). That is an ordinary ERROR, not a PM code.
  • It is not binary-coercible to or from text: pg_cast has no row for it in either direction. What you get is PostgreSQL's fallback I/O conversion, and only at explicit :: level. A text value will not pass as a markdown argument on its own, and a markdown value will not pass to a text function — length(knowledge.read('projects/auth')) fails with function length(markdown) does not exist. Write ::text and ::markdown yourself. Note that ::markdown re-runs the input function, so casting a text value re-checks pgmind.max_document_bytes.
  • It has no equality operator of its own — compare with ::text on both sides.
  • There is nothing special about it at the wire level: from an application, bind it as a normal string parameter. In psql, dollar-quote it as $md$…$md$ so apostrophes and backslashes survive.
  • Exactly two functions carry a (text) / (markdown) pair: knowledge.blocks and knowledge.links. For those two, an unadorned string literal arrives as unknown and PostgreSQL resolves it to text — the preferred type of the string category — so it means "a stored note at this path". Cast explicitly, knowledge.blocks($md$…$md$::markdown), when you mean to parse a document you are holding; otherwise you get PM002 with your document quoted back at you as a path.
  • Everywhere else there is no contest, so an unadorned literal is safe. knowledge.preamble and knowledge.properties take markdown and nothing else — knowledge.preamble('x'::text) fails with function knowledge.preamble(text) does not exist. knowledge.tags is overloaded on arity, tags() against tags(markdown), which never collides. The fragment and doc parameters of the writing functions are likewise markdown-only.

Example

psql
SELECT pg_typeof(knowledge.read('projects/auth')) AS type,
       octet_length(knowledge.read('projects/auth')::text) AS bytes;
   type   | bytes 
----------+-------
 markdown |   447
(1 row)

The seven kinds a block row can have. It is the type of pgmind.block.kind; the public functions return it widened to text.

pgmind.op_result In main

CREATE TYPE pgmind.op_result AS (revision uuid, block_ids uuid[]);

What the six block-level writing functions return: the revision they created, and the block ids the operation produced or preserved. knowledge.write is the exception — it returns a bare uuid.

Returns

ColumnTypeMeaning
revisionuuid The new head of the note. Pass it as the next call's expected_head.
block_idsuuid[] The blocks the operation is about, in document order. Which blocks those are depends on the operation — see each entry's Notes.

Notes

  • Consume it from FROM: SELECT revision FROM knowledge.update_block(…). The select-list form (f(…)).* is safe — a set-returning expression is evaluated once — but reads worse. While these returned a scalar composite it applied the write twice.

  FROM pg_attribute

 ORDER BY attnum;
  column   |  type  
-----------+--------
 revision  | uuid
 block_ids | uuid[]
(2 rows)

Parsing without storing

Five functions take a markdown value instead of a path and answer questions about it without touching a table. They are IMMUTABLE and PARALLEL SAFE, so you can use them in a generated column, a check constraint, or a validation step in front of your own writer.

Three of the five — blocks, links and tags — are overloads of reading functions and are documented with them below. All three need the cast. Each also has a text-taking overload, and an uncast literal — quoted or dollar-quoted — resolves to text, so pgmind reads your document as a path or a vault name instead of parsing it. Write $md$…$md$::markdown.

Changed

tags used to be the exception: it was overloaded on arity alone, so tags($md$…$md$) reached the parser. Now that tags(vault text DEFAULT NULL) exists, that same call resolves to the vault overload and raises PM018 — or, if the text happens to name a real vault, quietly answers a different question. Every example on this site carries the cast; check your own.

Reading a vault

Ten functions, none of which writes anything. Every one of them is scoped to the vault named by pgmind.vault_id, and every one of them raises PM002 rather than returning zero rows when the note does not exist — the distinction between "empty note" and "no note" matters to an agent.

knowledge.vaults In main

vaults(glob text DEFAULT '**'::text) → TABLE(vault_id uuid, name text, description text, created_at timestamptz)

List vaults, filtered by a glob over the name.

Scope — and RLS does not narrow this one

This lists every vault in the database. pgmind has no tenant concept, so narrowing a listing is knowledge.vaults('acme/**') and enforcing that narrowing is the application's job. See Multi-tenancy and access.

Row-level security does not cover it. pgmind.vault is the one table with no vault_id column to police — enable_vault_rls reports it as covered = false for exactly this reason. Measured: with the policy forced on and the session scoped to one vault, pgmind.note returns zero rows for the others while this function still returns all of their names. Since names are where an application puts its tenant and user hierarchy, treat them as disclosed to anyone who can run SQL on that connection, and do not expose this function through an agent-facing tool.

Parameters

NameTypeDefaultMeaning
globtext'**' Matched against the vault name, with the same */** rules as notes().

Example

psql
SELECT vault_id, name, description FROM knowledge.vaults('acme/**');
               vault_id               |          name           |         description         
--------------------------------------+-------------------------+-----------------------------
 019feaf0-…                           | acme/alice/instructions | Alice standing instructions
(1 row)

This is PostgreSQL's own text search — websearch_to_tsquery, ts_rank_cd, ts_headline, a GIN index. pgmind adds vault scoping, the tag filter, and the rule that you get the innermost matching block rather than it and its container. Nothing here is an embedding and nothing calls a model.

Notes

  • You get the innermost match, not its containers. A list item's content includes its own paragraph (RFC-002 D7), so - rotate the key matches twice; the container is dropped when one of its children also matched. The block you get back is both the better citation and the simpler thing to edit.
  • A query with no lexemes is a filter, not a failure. Empty, whitespace or all stop words means "no text predicate": tags and path still apply, and rank comes back NULL. With nothing else given there is no predicate at all and you get an empty result — not the whole vault. Postgres notes the lexeme-free query once, which is the only explanation you get for an empty result.
  • This is how you intersect tags. tagged() takes one tag; search('', tags => ARRAY['a','b']) is every block carrying both.
  • The text-search configuration is english, and it is fixed. That is the wrong stemmer for a vault that is not in English — an honest limitation, not an oversight. It lives in one place, pgmind.search_vector(text), which is also what the index is built on.
  • Very large blocks are indexed by their first 100,000 characters. to_tsvector refuses to build a vector past 1 MB, and a block of distinct words reaches that at around 849 KB — well inside what pgmind.max_document_bytes accepts. Truncating for the index means such a block is searchable by its opening rather than unstorable.
  • Fuzzy and typo-tolerant search do not exist; there is no pg_trgm dependency. Deliberate, and revisited when the exact-match half has been used in anger.

Writing

Seven functions change a note. All seven take the note's write lock, read everything they depend on from under it, check expected_head if you supplied one, and record a revision. pgmind never raises 40001 and never retries for you: a conflict is PM009, and the repair is to re-read.

Every entry states its identity outcome — which block ids survive the edit — because that is the difference between a citation that still resolves tomorrow and one that does not.

Composite return

Six of the seven return pgmind.op_result: insert_blocks, append_to_section, update_block, move_block, split_block and merge_blocks. knowledge.write returns a bare uuid. Call the six from FROM. The select-list form is safe now that they return a set; while they returned a scalar composite, SELECT (knowledge.append_to_section(…)).* was measured appending the same fragment twice from one statement.

Notes

  • All-or-nothing. One statement, one transaction: if element 400 has a bad path, elements 1–399 are rolled back too. That is the reason for the 1000 cap — not memory, but keeping the unit of retry something you can re-send.
  • No expected_head, deliberately. A batch is for ingestion, where you hold no prior head. Per element the semantics are ordinary write(): upsert, last-writer-wins, and byte-identical input mints no revision. Use write() when you need compare-and-swap.
  • It is not faster per note. Measured over a local socket, 500 notes cost the same 8.4 ms each whether sent as 500 statements, as one SELECT count(write(…)) FROM staging, or as one write_many — per-note parsing, hashing and extraction dominate that completely. What it removes is N round trips and N commits, which is worth real time against a remote database and nothing against a socket. Reach for it because a migration is one call, not because it is quick.
  • Duplicate paths within one batch are legal and applied in order — the second write of the same bytes is the usual no-op.

History and time travel

History is stored as pre-images: each revision records what the blocks it touched looked like before. Reading the past therefore costs something and reading the present costs nothing, which is the trade the whole engine is built around.

Administration

Nine functions in the pgmind schema plus pgmind_version in public. Reaching into pgmind is deliberate — the handbook calls it Law 11 — and several of these are destructive.

What is actually locked down today

Only pgmind.raise_error and pgmind.enable_vault_rls have had EXECUTE revoked from PUBLIC. excise, retain and the verify_* functions are callable by any role that can reach the schema, and none of them is SECURITY DEFINER. If that matters to you, revoke them yourself. RFC-005 D7 plans a grant-anchored boundary; it is not built.

{"path": "notes/x"} The note path as a string, wherever it appears. Calls delete_note.

Returns

Raises

  • PM012 the target names none of the three keys, or the content is still live at head and and_head is false.
  • PM013 the post-excision sweep found survivors. The transaction aborts, so no partial erasure and no log row commit.

Notes

  • The PM012 refusal precedes the dry-run short-circuit. A dry run against live content raises rather than reporting. Pass and_head => true to get a report.
  • The live-removal step is an ordinary audited write: for the literal and block forms it appears in history() as verb = 'write', not 'excise'. (RFC-005 D7.1 says 'excise'; the code does not.)
  • Redaction splices the text out of the surrounding content rather than nulling the row, so the shape of the document survives and the reader can see that something was removed.
  • The sweep enumerates text-bearing columns from pg_catalog, not information_schema — the latter is filtered by the caller's privileges and once let a canary survive in pgmind.block while verification reported success.
  • pgmind.excision_replay, which holds the executable target, is deliberately excluded from pg_dump: for the literal and path forms the target is the identifying data. The consequence is that restoring an old backup resurrects erased content, and there is no shipped replay function yet. See Not yet implemented.

pgmind.search_vector Internal

search_vector(content text) → tsvector -- IMMUTABLE, PARALLEL SAFE, STRICT

The one definition of what pgmind indexes for full-text search. Documented so you can see what search() is actually matching on, not so you call it.

It exists as a function rather than as inline SQL because the GIN index block_fts and the query inside search() must spell the expression identically — an expression index is used only on an exact match, and two copies drift into a sequential scan that still returns the right answer.

Returns

tsvector — to_tsvector('english', left(content, 100000)). Two deliberate choices are visible in that one line.

Notes

  • The configuration is english and is not settable. As a GUC it would let the index and the query disagree about which configuration built which row, which is a silently wrong answer; a fixed and documented English bias is the lesser evil. Changing it is redefining this function and REINDEXing — no table rewrite, which is why the index is here rather than in a generated column.

  • Redefining this function does not rebuild the index. If you change it, REINDEX INDEX pgmind.block_fts; or the index and the function are describing different vaults.

Server settings

Four GUCs, all USERSET, so an application role can change any of them for its own session with SET or — inside a pooled transaction — SET LOCAL.

pgmind.frame_every In main

integer default 50 min 1 max 1000000 USERSET

How many revisions pass between absolute history frames — full snapshots of both storage lanes.

Notes

  • It bounds the cost of read_as_of by the cadence rather than by the note's total depth: reconstruction anchors on the nearest frame at or above the target and walks backwards.

Error codes

pgmind raises errors in its own SQLSTATE class, PM. Every one carries a DETAIL: line naming the offending value, so an agent can repair by re-reading rather than by forcing. There are seventeen of them; RFC-004 A6 defined sixteen and PM017 arrived with the author setting.

The pgmind_* names below are the condition names written into DETAIL. They are not registered PostgreSQL condition names, so you cannot write WHEN pgmind_stale_head — catch by SQLSTATE.

Code Condition What it means What to do Raised by

PM002pgmind_note_not_found No live note at that path. A tombstoned note is not live. Check knowledge.notes(). If it was deleted, use undelete_note. Every reading function, every block operation, delete_note, move_note, undelete_note, and write when a concurrent rename beats it.
PM003pgmind_block_not_found The block id is unknown, belongs to another vault, or is not in the note the operation is about. Re-read knowledge.blocks(). Ids do not move between notes. update_block, move_block, split_block, merge_blocks, insert_blocks (anchor).
PM004pgmind_fragment_arity The fragment has the wrong number of top-level blocks, or carries frontmatter. Count the blocks: 1 for update and merge, ≥ 2 for split, ≥ 1 for insert. Frontmatter belongs to write(). insert_blocks, append_to_section, update_block, split_block, merge_blocks.
PM005pgmind_invalid_anchor The before/after pair is wrong, the anchor is illegal, or a section has nothing an append can attach to. insert_blocks takes one or neither; move_block takes exactly one. An anchor must be a top-level block or a list item. insert_blocks, move_block, append_to_section.
PM006pgmind_container_constraint The edit crosses a v1 container limit: re-parenting, nested containers in a fragment, a non-contiguous merge set. Do it with write() instead. v1 block ops reorder and replace; they do not restructure. update_block, move_block, split_block, merge_blocks.

PM016pgmind_stale_block expected_hash is not the block's current content hash. Re-read the block. Somebody edited it — this is the precise conflict, as opposed to PM009's note-wide one. update_block.
PM017pgmind_invalid_author pgmind.author is longer than 200 characters. Shorten it. The limit is characters, not bytes, so a limit never cuts a name in half. Every function that records a revision.
PM018pgmind_vault_not_found No vault has that name or id. Check knowledge.vaults(), or create it. A vault id nobody registered is an error, not a new empty vault — that is what stops a typo becoming a vault you can never find again. Every vault-scoped function, and pgmind.vault_id itself.
PM019pgmind_batch_arity The batch arrays disagree in length, an element is NULL, or the batch is over 1000 notes. Fix the arrays. The DETAIL names the element index. Distinct from PM004, which is about blocks inside one document. write_many.

Catching one

In plpgsql, match on the SQLSTATE string. The condition names are pgmind's vocabulary, not PostgreSQL's, so they are not available to WHEN.

psql
DO $fn$
BEGIN
  PERFORM knowledge.write('projects/auth', $md$# Auth$md$,
          expected_head => '00000000-0000-0000-0000-000000000000');
EXCEPTION WHEN sqlstate 'PM009' THEN
  RAISE NOTICE 'head moved: %', sqlerrm;
END
$fn$;
NOTICE:  head moved: pgmind: expected_head is not the note's current head
DO

A retry loop is the same shape with the PERFORM inside a bounded LOOP; there is a worked one in the cookbook.

From a client library, read the SQLSTATE off the error object — psycopg exposes it as e.sqlstate, node-postgres as err.code, JDBC as getSQLState() — and branch on the five characters. The human-readable condition name is the first token of DETAIL, before the em dash, if you would rather log that. Do not parse the ERROR: message text: it is prose and it will change.
