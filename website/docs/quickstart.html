Manual · Quick start

Quick start

Ten minutes from an empty database to a citation that points at one paragraph at one revision — by way of the build, a seven-note vault, and the five operations an agent actually needs.

How the transcripts below are elided

Every block was executed against PostgreSQL 18 and its output pasted back. UUIDs are shortened to 019fd625-… because yours will differ, and the CONTEXT line that every pgmind error carries is dropped after the first error shows it.

What pgmind is

A PostgreSQL extension that stores an Obsidian-shaped markdown vault — notes at paths, headings, paragraphs, list items, wiki-links, tags — as relational rows. You write markdown in and the same bytes come back out; in between, every structural piece of the document is a block: a row with a UUID, a content hash and a history.

No model is called anywhere inside it and it opens no network sockets. That is an architecture law, not a gap in the current build — no embedding step, no summarizer, no background worker, nothing to allowlist. If you want vectors you fill a table of your own with your own pipeline and join to it.

Why not a folder of markdown

A directory handles one writer beautifully. Put it behind a backend and the failures are all the same failure: two requests write the same note and one disappears, "what links here" becomes a grep of the whole tree, history means shelling out to git in a request handler, and every tenant needs a directory somebody has to prove you stayed inside. pgmind answers each of those with the thing the database was already good at — a row, a lock, a transaction, a query.

Where the project is

Research pre-alpha, version 0.0.1. Phases 0–3 have exited, Phase 4 was cut, and Phase 5 is in progress — it ends at the first public release, 0.1.0. Everything on this page runs today, but the SQL surface is being frozen for 0.x right now and there is no upgrade path between builds: you drop the extension and rebuild the vault.

When to use it, and when not to

The honest scope is phases 0–3: the vault model, block-level operations, versioning, concurrency control and erasure. Enough to build against, not enough to serve traffic on.

Reach for pgmind when Stay on files when
Several agents, workers or request handlers write the same vault and a lost write is a real bug. One writer, one machine, offline. A folder plus git is simpler, faster, and already works. pgmind adds a database dependency and buys you nothing.
You need to cite a specific paragraph and resolve that citation later, after the note has changed. The vault is small enough that reading every file on every request is fine.
Backlinks, tags, orphans or graph walks are queries you run often rather than once. A human edits the notes in an editor and nothing else touches them.
Tenants must be isolated, and you would rather prove it with row security than with directory naming. You want a folder and a vault kept continuously in step by a daemon. pgmind deliberately does not do that; it exports and imports on demand, byte for byte.
You already run PostgreSQL and would rather have one backup than two systems that drift. You need a stable, versioned API. This one changes between commits.

Install

There is no binary release; you build it. A few minutes on a warm cache — the first make setup compiles a PostgreSQL from source and is considerably longer.

Prerequisites

  • Rust, pinned by rust-toolchain.toml to 1.97.1. rustup installs it for you on first build; you do not pick a version.
  • macOS only: pkgconf and icu4c, needed to compile the pgrx-managed PostgreSQL.
  • Python 3.10+, only if you intend to run make eval (the benchmark gates).
shell
brew install pkgconf icu4c          # macOS only
git clone https://github.com/MarosiLabs/pgmind.git
cd pgmind

Build and test

Three canonical targets. CI runs exactly these.

shell
make setup   # install the pinned cargo-pgrx, then compile a PostgreSQL 18
             # into ~/.pgrx — self-contained and writable. This is the slow one.
make build   # build the extension (PG=18 by default; make build PG=16)
make test    # core unit tests, then cargo pgrx test inside a real PostgreSQL
Why pgrx compiles its own PostgreSQL, and what the Makefile does for you

System installs are traps: Homebrew's libpq ships a client-only pg_config, and macOS refuses to let anything write an extension into Postgres.app's protected bundle.

On macOS the Makefile puts keg-only icu4c on PKG_CONFIG_PATH and exports SDKROOT for you, so bindgen can find the system headers.

Run it

cargo pgrx run builds the extension, installs it into the managed cluster, starts the server and drops you at a psql prompt on a scratch database.

shell
cd extension
cargo pgrx run pg18 --no-default-features --features pg18

CREATE EXTENSION

psql
CREATE EXTENSION pgmind;
SELECT pgmind_version();
WARNING:  pgmind: lz4 toast compression unavailable on this server; using default
CREATE EXTENSION
 pgmind_version
----------------
 0.0.1
(1 row)
Why the lz4 warning is harmless, and why the install needs a superuser

The lz4 line is a WARNING, not an error. pgmind asks for lz4 TOAST compression on its large text columns and falls back to the server default when the build does not have it — which a pgrx-compiled PostgreSQL usually does not. Nothing else changes.

The control file sets superuser = true, trusted = false and relocatable = false. So CREATE EXTENSION needs a superuser, a non-superuser database owner cannot install it into their own database, and the schemas are fixed at knowledge and pgmind. Application roles never need superuser — only the install does.

The settings are invisible until the library loads

pgmind's four GUCs are registered by _PG_init, which PostgreSQL runs the first time a backend actually loads the shared library. Installing the extension does not do that for later sessions:

psql · a new connection
\c
SHOW pgmind.frame_every;
You are now connected to database "pgmind" as user "amin".
ERROR:  unrecognized configuration parameter "pgmind.frame_every"

Call any pgmind function — or load the library explicitly — and all four appear:

psql
LOAD 'pgmind';
SHOW pgmind.frame_every;
SHOW pgmind.max_document_bytes;
SHOW pgmind.author;
SHOW pgmind.vault_id;
LOAD
 pgmind.frame_every
--------------------

(1 row)

 pgmind.max_document_bytes
---------------------------

(1 row)

 pgmind.author
---------------

(1 row)

           pgmind.vault_id
--------------------------------------
 00000000-0000-0000-0000-000000000000
(1 row)

pgmind.author is empty by default, which means revisions are attributed to current_user. Set it and the value is recorded as written — the writer's own claim about itself, never authenticated.

Why SET works before the load even though SHOW does not

PostgreSQL accepts a placeholder setting in a namespace it does not know yet, so SET pgmind.vault_id = … succeeds before _PG_init has run and the value is honoured once it does. It is only SHOW that fails. If you set the GUC from a connection-pool startup hook, nothing is wrong.

Installing into a cluster you already run

Put that server's pg_config on PATH — the real one from the server package, not libpq's — and let pgrx write into it. The role running CREATE EXTENSION must be a superuser.

shell
which pg_config                     # must be the server's, not libpq's
cd extension
cargo pgrx install --release --no-default-features --features pg18

Your first note

A note is markdown at a path — no create step, no schema to declare. knowledge.write takes a path and a document and returns the id of the revision it created, or the current head when the bytes are identical to what is already stored, because then no revision is written.

psql
SELECT knowledge.write('projects/auth', $md$---
title: Auth
tags: [architecture, active]
owner: platform
---

# Auth

The service that issues and rotates credentials. Owned by [[people/ada]].

## Decisions

- [[oauth2]] over server sessions, see [[rfc/auth-01]] #architecture
- Refresh tokens rotate every 24h #decision ^rotation
- Access tokens live 15 minutes, no exceptions

## Runbook

Key rotation is [[runbooks/rotate-keys|documented separately]].

## Log

Migrated the session store.
$md$);
                write
--------------------------------------
 019fd625-ce4d-…
(1 row)

Markdown is full of quotes and backslashes, so the examples pass it dollar-quoted as $md$…$md$. From an application, bind it as an ordinary text parameter — the markdown type is nothing special at the wire level.

One bullet is two rows

Rows 3 and 4 are the same bullet: a list_item container and the paragraph inside it. Markers land on the innermost block, which is why ^rotation is on row 6 and not row 5.

Why, and where the vault's 48 blocks come from

CommonMark says a list item holds block content, and pgmind stores the parse rather than a flattened summary of it, so both rows exist. That is why the seven-note vault you are about to finish reports 48 blocks for maybe thirty visible lines of prose:

psql
SELECT kind, count(*)
FROM   knowledge.notes() n, LATERAL knowledge.blocks(n.path) b
GROUP  BY kind ORDER BY count(*) DESC;
   kind    | count
-----------+-------
 paragraph |    24
 list_item |    13
 heading   |    11
(3 rows)

Thirteen list items, each with a paragraph inside it, is 26 of the 48. Internalise it before you write a query that counts paragraphs and gets an answer twice the size you expected.

Links, including the broken ones

Every wiki-link, transclusion, block reference and markdown link is an edge row. Edges that resolve to nothing are stored anyway, with a reason, so a broken-link report is a query rather than a crawl. Nothing else exists in the vault yet, so every link dangles:

psql
SELECT kind, target, alias, resolved_path, dangling_reason
FROM   knowledge.links('projects/auth')
ORDER  BY target;
   kind   |        target        |         alias         | resolved_path | dangling_reason
----------+----------------------+-----------------------+---------------+-----------------
 wikilink | oauth2               |                       |               | missing
 wikilink | people/ada           |                       |               | missing
 wikilink | rfc/auth-01          |                       |               | missing
 wikilink | runbooks/rotate-keys | documented separately |               | missing
(4 rows)

Write the notes they point at and the edges repair themselves inside the same transaction that creates each note. These six writes finish the demo vault that every page of this manual uses.

psql
SELECT knowledge.write('rfc/auth-01', $md$# RFC-AUTH-01: token rotation

The operational steps live in the [rotation runbook](runbooks/rotate-keys.md).

---

2. Generate the new key pair

Finding it again

Ranked full-text search over blocks, on an index the write path keeps current. Nothing to refresh, and no embedding anywhere.

psql
SELECT path, round(rank::numeric, 4) AS rank, excerpt
FROM   knowledge.search('rotate keys');
         path         |  rank  |                    excerpt
----------------------+--------+-------------------------------------------
 projects/auth        | 0.0909 | **Key** **rotation** is [[runbooks/rotate…
 runbooks/rotate-keys | 0.0323 | **Rotate** the signing **keys**
(2 rows)

The query is websearch_to_tsquery syntax — bare words are ANDed, "quoted phrases" are literal, a leading - excludes. It cannot be made to raise, because a search box is fed whatever gets typed. Narrow with path => for one note or tags => for blocks carrying every tag listed; drop the text entirely and it is a pure tag intersection. You get the innermost matching block, so a bullet is not returned twice, and its block_id is both a citation and an edit target.

The five moves an agent makes

Everything an agent does to a vault is one of these. None of them requires reading or rewriting the whole note.

1. Read one section

read_section returns the heading and everything under it, as markdown, ready to drop into a prompt. The heading path is the chain of heading texts, outermost first.

psql
SELECT knowledge.read_section('projects/auth', ARRAY['Auth','Decisions']);
                             read_section
----------------------------------------------------------------------
 ## Decisions                                                        +
                                                                     +
 - [[oauth2]] over server sessions, see [[rfc/auth-01]] #architecture+
 - Refresh tokens rotate every 24h #decision ^rotation               +
 - Access tokens live 15 minutes, no exceptions                      +
(1 row)

2. Append to a section

The workhorse. It resolves the anchor after taking the note lock, so it never reads the note first and never guesses where the section ends.

psql
SELECT * FROM knowledge.append_to_section('projects/auth', ARRAY['Auth','Log'],
    $md$Rotated the signing key.$md$);
               revision               |               block_ids
--------------------------------------+----------------------------------------
 019fd625-ce8b-…                      | {019fd625-ce89-…}
(1 row)
psql
SELECT knowledge.read_section('projects/auth', ARRAY['Auth','Log']);
        read_section
-----------------------------
 ## Log                     +
                            +
 Migrated the session store.+
                            +
 Rotated the signing key.   +
(1 row)

Like all six block operations it returns SETOF pgmind.op_result — one row, (revision, block_ids) — so you read it from FROM.

3. Patch one block

A ^marker in the markdown gives a block a name you chose, easier to carry around than a UUID. Here ^rotation finds the block and replaces it:

psql
SELECT * FROM knowledge.update_block(
    (SELECT block_id FROM knowledge.blocks('projects/auth')
     WHERE  block_ref_id = 'rotation'),
    $md$Refresh tokens rotate every 12h #decision ^rotation$md$);
               revision               |               block_ids
--------------------------------------+----------------------------------------
 019fd625-ce8e-…                      | {019fd625-ce4d-78a9-…}
(1 row)

The returned block id is the same id the block had before the edit: updating a block asserts that identity is kept, so anything that cited it still points at it.

4. Cite a block

A citation is a path, a block, and the revision you read it at — three columns you already have:

psql
SELECT n.path || '#^' || b.block_ref_id || ' @ ' || n.head_revision AS citation
FROM   knowledge.notes('projects/auth') n,
       LATERAL knowledge.blocks(n.path) b
WHERE  b.block_ref_id = 'rotation';
                            citation
----------------------------------------------------------------
 projects/auth#^rotation @ 019fd625-ce8e-…
(1 row)

That string survives being written into an answer, a log or another note. Resolving it later gives the exact text as of that revision, however much the note has moved on since:

psql
SELECT ord, content
FROM   knowledge.blocks_as_of('projects/auth',
         (SELECT head_revision FROM knowledge.notes('projects/auth')))
WHERE  block_id = (SELECT block_id FROM knowledge.blocks('projects/auth')
                   WHERE  block_ref_id = 'rotation');
 ord |                  content
-----+-------------------------------------------
   6 | Refresh tokens rotate every 12h #decision
(1 row)

5. Look at what changed

psql
SELECT seq, verb, author, source, blocks_changed, reconstructable
FROM   knowledge.history('projects/auth');
 seq |     verb      | author | source | blocks_changed | reconstructable
-----+---------------+--------+--------+----------------+-----------------
   2 | update_block  | amin   | api    |              2 | t
   1 | insert_blocks | amin   | api    |              1 | t
   0 | write         | amin   | api    |             13 | t
(3 rows)

source is api for every operation the shipped extension performs. The append shows up as insert_blocks because append_to_section resolves the anchor and then delegates. reconstructable is the honest flag: t means the note can still be rebuilt as of that revision, and retention or an excision — erasing a revision's text on request — can turn it f.

diff compares two revisions block by block. The one-line edit shows as two changed blocks: the list item and the paragraph inside it.

psql
SELECT change, left(before, 34) AS before, left(after, 34) AS after
FROM   knowledge.diff('projects/auth',
         (SELECT revision FROM knowledge.history('projects/auth') WHERE seq = 1),
         (SELECT revision FROM knowledge.history('projects/auth') WHERE seq = 2));
 change  |               before               |               after
---------+------------------------------------+------------------------------------
 changed | Refresh tokens rotate every 24h #d | Refresh tokens rotate every 12h #d
 changed | Refresh tokens rotate every 24h #d | Refresh tokens rotate every 12h #d
(2 rows)

Two agents, one note

This is the part that does not work in a folder. Three cases, in increasing order of how little they cost you.

The conflict you want

Pass the revision you read as expected_head and a stale write is refused instead of silently applied. Here it is handed the note's very first revision, two revisions out of date:

psql
SELECT knowledge.write('projects/auth', $md$# Auth

Rewritten from a stale read.
$md$, expected_head => (SELECT revision FROM knowledge.history('projects/auth')
                        WHERE seq = 0));
ERROR:  pgmind: expected_head is not the note's current head
DETAIL:  pgmind_stale_head — note projects/auth: expected 019fd625-ce4d-…, head is 019fd625-ce8e-…
CONTEXT:  PL/pgSQL function pgmind.raise_error(text,text,text) line 3 at RAISE

SQLSTATE PM009. The DETAIL always carries the offending value, and the repair is to re-read and try again, never to force. Omitting expected_head means "I do not care what was there" — right for a first write, wrong for a read-modify-write.

The conflict that isn't

Two agents appending to the same section do not conflict at all. Both writes land, in lock order: session A holds a transaction open, and session B waits on the note's row lock.

psql · session A
BEGIN;
SELECT * FROM knowledge.append_to_section('projects/auth', ARRAY['Auth','Log'],
    $md$Agent A rotated the staging key.$md$);
SELECT pg_sleep(2);
COMMIT;
BEGIN
               revision               |               block_ids
--------------------------------------+----------------------------------------
 019fd626-9a4e-…                      | {019fd626-9a46-…}
(1 row)

COMMIT
psql · session B, while A still holds the lock
SELECT * FROM knowledge.append_to_section('projects/auth', ARRAY['Auth','Log'],
    $md$Agent B rotated the production key.$md$);
               revision               |               block_ids
--------------------------------------+----------------------------------------
 019fd626-a291-…                      | {019fd626-a285-…}
(1 row)
psql
SELECT knowledge.read_section('projects/auth', ARRAY['Auth','Log']);
            read_section
-------------------------------------
 ## Log                             +
                                    +
 Migrated the session store.        +
                                    +
 Rotated the signing key.           +
                                    +
 Agent A rotated the staging key.   +
                                    +
 Agent B rotated the production key.+
(1 row)

Nothing was lost and nobody retried: append_to_section resolves its anchor after acquiring the lock, so B sees A's paragraph and lands after it. This is the only operation for which a race is not a conflict — which is exactly why an agent log should be an append rather than a rewrite.

The false conflict, removed

expected_head guards the whole note, so two agents patching different paragraphs still collide. That is real serialization but a false conflict: the edits do not overlap. Agent B reads the head and the block it intends to edit (\gset is how psql holds a value between statements):

psql · agent B reads
SELECT head_revision AS head FROM knowledge.notes('projects/auth') \gset
SELECT block_id AS bid, encode(content_hash, 'hex') AS bhash
FROM   knowledge.blocks('projects/auth') WHERE ord = 1 \gset

Agent A now edits a different paragraph, moving the head:

psql · agent A writes
SELECT * FROM knowledge.update_block(
    (SELECT block_id FROM knowledge.blocks('projects/auth') WHERE ord = 8),
    $md$Access tokens live 10 minutes, no exceptions$md$);
               revision               |               block_ids
--------------------------------------+----------------------------------------
 019fd626-a2c6-…                      | {019fd626-99de-…}
(1 row)

Agent B, guarding on the note, is rejected — though its paragraph never moved:

psql · agent B, guarding the note
SELECT * FROM knowledge.update_block(:'bid',
    $md$The service that issues and rotates credentials. Owned by [[people/ada]], on call.$md$,
    expected_head => :'head');
ERROR:  pgmind: expected_head is not the note's current head
DETAIL:  pgmind_stale_head — note projects/auth: expected 019fd626-a291-…, head is 019fd626-a2c6-…

Guard on the block instead. expected_hash is compare-and-swap at block granularity: it fails only if that paragraph's content changed.

psql · agent B, guarding the block
SELECT * FROM knowledge.update_block(:'bid',
    $md$The service that issues and rotates credentials. Owned by [[people/ada]], on call.$md$,
    expected_hash => decode(:'bhash', 'hex'));
               revision               |               block_ids
--------------------------------------+----------------------------------------
 019fd626-a2d1-…                      | {019fd626-99de-…}
(1 row)

Run it a second time and you get PM016 (pgmind_stale_block) instead — the guard did its job. What expected_hash removes is the false conflict, not the serialization: both agents still queue on the note's row lock, and both succeed. Of the write operations only update_block accepts it; the rest take expected_head alone.

One vault per tenant

Every row in pgmind carries a vault_id. One session setting picks which vault the knowledge functions see. Nothing else changes — same schema, same functions, same connection.

SELECT * FROM knowledge.create_vault('tenant-b',
    vault_id => '11111111-1111-1111-1111-111111111111');
SET pgmind.vault_id = '11111111-1111-1111-1111-111111111111';
SELECT vault_id, notes, blocks FROM knowledge.stats();

--------------------------------------+----------

(1 row)

SET

--------------------------------------+-------+--------

(1 row)

The GUC scopes; it does not defend

pgmind.vault_id is USERSET. Any session can set it to any value, and a session that can reach the pgmind tables directly can read every tenant regardless. On its own it is a convenience for addressing, not a boundary. The boundary is row-level security plus a grant set that keeps application roles out of the pgmind schema. Inside a connection pool, use SET LOCAL inside the transaction so the value cannot leak to the next borrower of the connection.

Admin One call installs the policies. It is idempotent — it drops each policy before creating it, which is why the first run is noisy.

psql
SELECT * FROM pgmind.enable_vault_rls();

One row per table, so you can see what it could not cover. Ten tables carry a vault_id and get a policy. Two do not, and are reported rather than skipped in silence: pgmind.excision_replay, which holds the identifying data an erasure removed, and pgmind.vault, the registry itself — which means knowledge.vaults() lists every vault's name whatever the policy says. Content is scoped; names are not.

RLS also does not apply to a superuser, or to a table's owner unless you force it: pgmind.enable_vault_rls(force => true) covers the owner. Run your application as a role that owns nothing.

When something goes wrong

pgmind raises errors in its own SQLSTATE class, PM. The DETAIL names the error condition and carries the offending value, and every one is catchable — EXCEPTION WHEN sqlstate 'PM009' in plpgsql, or by reading SQLSTATE from your driver.

Code You will see Cause → fix
PM001
path		 pgmind: invalid note path The path breaks the grammar — leading or trailing slash, empty segment, . or .., over 1 024 bytes. Check it with pgmind.path_is_valid; pgmind.path_normalize trims and NFC-normalises but does not validate.
PM002
missing		 pgmind: note not found No live note at that path in this vault: a typo, the wrong pgmind.vault_id, or a path that differs by case — paths are case-sensitive. Reading an invalid path also lands here rather than on PM001.
PM003
missing		 pgmind: block not found The id is stale or foreign: nothing live in this vault carries it — another vault, a deleted note, or a block some later write removed. A cached id normally survives editing: a block keeps its id through a whole-note rewrite, matched by content hash, by its ^id marker, or by the rebinder (the pass that re-attaches ids to blocks that moved or changed), and is re-minted only when none of those match. Re-read knowledge.blocks().
PM004
fragment		 pgmind: split_block fragment must contain at least two blocks Fragment arity. Each operation demands a specific number of top-level blocks: update_block exactly one, split_block two or more. The DETAIL tells you what it parsed.
PM005
anchor		 pgmind: give before OR after, not both An illegal anchor. Give insert_blocks one of before/after, or neither to append at the end. Also raised as anchor must be a top-level block or a list item when the anchor cannot carry an insert — the paragraph nested inside a bullet, for instance. Anchor on the list_item row instead.
PM007
section		 pgmind: section not found
pgmind: no section with that heading path		 No section matches that heading path. Read heading_path off knowledge.blocks() rather than guessing it from the markdown: the normalisation keeps the plain inline text only — # marks and emphasis dropped, wiki-links reduced to alias-else-target, a trailing ^id stripped, NFC, trimmed. append_to_section anchors on the heading itself when the section has no content yet, so the first append into a freshly created section works.
PM009
conflict		 pgmind: expected_head is not the note's current head Somebody wrote since you read. Re-read, re-apply, retry — never retry with the same expected_head. If the edit is confined to one block, switch to update_block(…, expected_hash => …); if it is an append, switch to append_to_section and drop the guard entirely. Passing expected_head for a path with no live note also raises PM009, never a silent create.
PM016
conflict		 pgmind: expected_hash is not the block's current content hash That block changed under you. Re-read the block, decide whether your edit still applies, and rebuild it. The DETAIL prints both hashes.

All nineteen codes, with the functions that raise each, are in the SQL reference.

Composite returns, and the trap that used to be here

The six block operations return SETOF pgmind.op_result — one row, (revision, block_ids). Read them from FROM:

psql
SELECT knowledge.write('notes/trap', $md$# Trap

## Log

First line.
$md$);

SELECT * FROM knowledge.append_to_section('notes/trap', ARRAY['Trap','Log'],
                                          $md$Appended once.$md$);

SELECT knowledge.read('notes/trap');
                write                 
--------------------------------------
 019ffe43-8c62-…
(1 row)

               revision               |               block_ids                
--------------------------------------+----------------------------------------
 019ffe43-8c6b-…                      | {019ffe43-8c69-…}
(1 row)

      read      
----------------
 # Trap        +
               +
 ## Log        +
               +
 First line.   +
               +
 Appended once.+
 
(1 row)

Until recently these returned a scalar composite, and SELECT (knowledge.append_to_section(…)).* applied the edit twice — PostgreSQL expands (f(x)).* by evaluating f once per output column. Returning a set fixed it: a set-returning expression in the select list is evaluated once. The select-list form is now safe, and FROM remains the clearer way to read a row.

"function is not unique"

Several functions are overloaded on their second argument — read_as_of takes a uuid, a bigint or a timestamptz. An untyped literal or a bare NULL leaves PostgreSQL nothing to choose on:

psql
SELECT knowledge.read_as_of('projects/auth', NULL);
ERROR:  function knowledge.read_as_of(unknown, unknown) is not unique
HINT:  Could not choose a best candidate function. You might need to add explicit type casts.

Cast the argument: 0::bigint, $1::uuid, now() - interval '7 days'. The same message with a different cause appears after a rebuild — install a build whose signature changed without dropping the extension first and both versions end up in pg_proc, making every call ambiguous. There is no upgrade path in pre-alpha, so the fix is DROP EXTENSION pgmind CASCADE; followed by CREATE EXTENSION pgmind; — which drops your vault. Check with \df knowledge.read_as_of before you assume it is a type problem.
