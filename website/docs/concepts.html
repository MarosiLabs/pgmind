Manual / Concepts

Concepts

Everything pgmind stores has a name, and most of the surprises come from not knowing which name means what. This page defines the nouns — vault, note, path, tile, block, edge, tag, revision — and then spells out the markdown dialect exactly, because that is where a vault stops being “markdown” and starts being data you can query.

How to read this page

Every example was executed against the seven-note demo vault that Quick start builds, in the order they appear. A few of them write, and each says so; the writes clean up after themselves except where a later section depends on them. UUIDs and content hashes are elided — yours will differ.

The vault model

A vault is a set of notes. A note is markdown at a path. Everything below the note is derived from the note's bytes on every write, and everything above it is one uuid column.

the shape of the data
vault                  one uuid, on every row (GUC: pgmind.vault_id)
 └── note              path, preamble, properties, head_revision
      ├── tile[]       byte lane   — the source spans of the top-level nodes
      │                              preamble ‖ tile[0] ‖ tile[1] ‖ … == the file
      ├── block[]      semantic lane — one row per addressable unit
      │     ├── edge[] wikilink | transclusion | blockref | mdlink
      │     └── tag[]
      └── revision[]   append-only: seq, verb, author, source, message

The two lanes are the whole design. The byte lane exists so that knowledge.read() can hand back the file the writer handed in, byte for byte, without re-rendering anything. The semantic lane exists so that a paragraph has an id, a hash, a section, a position and a history. Neither lane is a view over the other; both are written in the same transaction from the same parse. Internals covers why.

The seeded vault, counted:

psql
SELECT notes, blocks, edges_resolved, edges_dangling, tags, revisions, bytes
  FROM knowledge.stats();
 notes | blocks | edges_resolved | edges_dangling | tags | revisions | bytes
-------+--------+----------------+----------------+------+-----------+-------
     7 |     48 |             16 |              2 |    9 |         7 |  1383
(1 row)
Why seven short notes are 48 blocks

A bulleted list item produces two rows: the list_item and the paragraph inside it. That is deliberate — the item is the thing you cite and reorder, the paragraph is the thing whose text changed — but it doubles the row count of any list-heavy note, and it means a block count is not a “paragraph count”. See Blocks.

Notes and paths

A path is the note's identity to a human and to a link. It is not the note's identity to the database — that is a uuid, and a move_note keeps it — but every public function addresses notes by path.

RuleLegalRejected
UTF-8, Unicode NFCcafé/notes in NFC the same text in NFD (e + combining acute)
Case-sensitiveprojects/auth nothing — but Projects/Auth is a different note
/-separated, no empty segmenta/b/c /a, a/, a//b
No . or .. segmenta/dot.name a/./b, a/../b, .

No leading or trailing whitespace, in any segment a/b a, a , a/ b
At most 1024 bytes total1024 bytes1025 bytes

Two functions, and they do different jobs. pgmind.path_normalize trims and NFC-canonicalizes and validates nothing; pgmind.path_is_valid validates and normalizes nothing. The write path runs them in that order, which is why a path that is only almost legal — surrounding whitespace, NFD from a macOS filename — is accepted after normalization while a structurally broken one is not:

psql
SELECT p AS candidate, octet_length(p) AS bytes,
       pgmind.path_is_valid(p) AS valid,
       pgmind.path_is_valid(pgmind.path_normalize(p)) AS valid_normalized
  FROM unnest(ARRAY['projects/auth', ' projects/auth ', '/bad/', 'a//b',
                    'a/../b', 'a\b', '.', 'cafe' || U&'\0301']) AS p;
    candidate    | bytes | valid | valid_normalized
-----------------+-------+-------+------------------
 projects/auth   |    13 | t     | t
  projects/auth  |    15 | f     | t
 /bad/           |     5 | f     | f
 a//b            |     4 | f     | f
 a/../b          |     6 | f     | f
 a\b             |     3 | f     | f
 .               |     1 | f     | f
 café            |     6 | f     | t
(8 rows)

The last row is the NFD case: six bytes for a five-byte word, invalid as written, valid once normalized. This is not cosmetic — an NFD path and an NFC path are different strings to PostgreSQL, so without normalization a vault imported from a macOS filesystem would contain two notes that look identical in every editor.

Basenames and globs

The last segment is the basename. It is what knowledge.notes().title reports, and it is the unit of basename link resolution (below).

knowledge.notes() takes a git-style glob, and only a git-style glob: * matches within one segment, ** matches zero or more whole segments, and nothing else is special. There are no character classes, no ?, no braces. A ** is only recognized as a complete segment.

psql
SELECT g AS glob, (SELECT count(*) FROM knowledge.notes(g)) AS matches
  FROM unnest(ARRAY['**', '*', 'projects/*', 'projects/**',
                    '**/a*', 'Projects/**']) AS g;
    glob     | matches
-------------+---------
 **          |       7
 *           |       1
 projects/*  |       1
 projects/** |       1
 **/a*       |       3
 Projects/** |       0
(6 rows)

Three things in that output are worth naming. * matches only the single-segment note (index), because * never crosses a /. projects/** matches projects/auth even though ** stands for zero segments there. And Projects/** matches nothing: globs are as case-sensitive as paths.

Globs are capped at 4096 bytes, and an empty glob is an error — a pattern is matched against every candidate path, so an unbounded pattern would be an unbounded per-row cost. pgmind computes the glob's longest literal prefix (projects/ for projects/*, the empty string for **) and pushes it down to the path index before matching, so a prefixed glob does not scan the vault.

One place the spec and the code disagree

RFC-002 D8 lists “no .md suffix” as part of the path grammar, on the grounds that filename mapping is a different concern. pgmind.path_is_valid('notes/a.md') returns true. The suffix is a convention here, not a constraint; if you import a folder of files, strip it yourself.

A note's anatomy

A note is stored as a preamble followed by a list of tiles. The preamble is the frontmatter plus any leading trivia. A tile is the source span of one top-level child of the document — one heading, one paragraph, one whole list, one whole blockquote — including the blank lines that follow it. Concatenating the preamble and the tiles in order reproduces the input exactly:

psql
SELECT knowledge.read('rfc/auth-01')::text = $md$# RFC-AUTH-01: token rotation

Rotation policy for [[projects/auth]]. #architecture #decision

The operational steps live in the [rotation runbook](runbooks/rotate-keys.md).
$md$ AS byte_identical;
 byte_identical
----------------
 t
(1 row)

That property holds for every input, including tabs, setext headings, indented code, CRLF line endings and trailing whitespace. pgmind never “cleans up” markdown. Normalization happens only inside the content hash, where it cannot be observed by a reader.

The preamble is available without storing anything, over a markdown value:

psql
SELECT knowledge.preamble($md$---
title: Auth
tags: [architecture]
---

# Auth
$md$) AS preamble;
       preamble
----------------------
 ---                 +
 title: Auth         +
 tags: [architecture]+
 ---                 +
                     +

(1 row)

Tiles are a storage and serialization unit, not an addressing unit: no public function exposes them, and you never cite one. The reason they exist is that nested blocks cannot be serialized on their own: a paragraph inside a blockquote has a span whose bytes still contain the >  prefixes, so re-emitting that slice would not be a faithful standalone document. Anything that rewrites a nested block re-serializes the whole tile that contains it.

Blocks

A block is the addressable unit: the thing that carries an id, a content hash, a citation and a revision. There are seven kinds, and two markdown constructs that are deliberately not blocks.

KindBlock? Can carry ^idNotes
headingyesyes levels 1–6; ATX and setext both, preserved as written. attrs: level, setext, text
paragraphyesyes
list_itemyesyes each item is a block; attrs: ordered, start, tight, and task/checked for task items
code_blockyesno fenced and indented; attrs: fenced, info
tableyesno one block per table; rows are not separately addressable in v1
thematic_breakyesno
html_blockyesno opaque; never interpreted
block_quotecontainer— no row of its own; its children are blocks, and quotes nest
listcontainer— no row of its own; carries its style in each item's attrs

Containers having no rows is the single most load-bearing choice here. It means a quoted paragraph is a first-class, citable, patchable paragraph; it also means a whole blockquote cannot be cited or updated as a unit. Here is a document containing every shape at once, parsed without being stored:

   2 | list_item      |        | {Title}      | an item

  • ord is document order over all blocks, nested ones included. It is recomputed on every write; it is a position, never an identity.
  • parent (called parent_block in the stored form) points at the enclosing addressable block. The nested item's parent is the outer item, not the inner list. The quoted paragraph has no parent at all, because a blockquote is not addressable.
  • content is the normalized logical text that was hashed, not the raw bytes. The quoted line arrives without its > ; the item arrives without its - . Raw bytes are recoverable from span_start/span_end.
  • ATX markers survive into content (# Title): the marker is the heading's syntax, not container decoration.
Cast your markdown literals

blocks, links and tags each have two overloads — one taking a note path, one taking a markdown value. An unadorned string literal is unknown, and PostgreSQL resolves it to the text overload, so pgmind goes looking for a note whose path is your entire document: 

ERROR:  pgmind: note not found
DETAIL:  pgmind_note_not_found — path "A [[projects/auth]] link."

Write $md$…$md$::markdown whenever you mean the parser. Every parse-only example on this page does.

Sections and heading paths

There is no section table. A section is a query: every block whose heading_path starts with the headings you care about. heading_path is the heading text of the enclosing headings, outermost first, and it is recomputed on every write.

psql
SELECT ord, kind, heading_path FROM knowledge.blocks('projects/auth') ORDER BY ord;
 ord |   kind    |   heading_path
-----+-----------+------------------
   0 | heading   | {}
   1 | paragraph | {Auth}
   2 | heading   | {Auth}
   3 | list_item | {Auth,Decisions}
   4 | paragraph | {Auth,Decisions}
   5 | list_item | {Auth,Decisions}
   6 | paragraph | {Auth,Decisions}
   7 | list_item | {Auth,Decisions}
   8 | paragraph | {Auth,Decisions}
   9 | heading   | {Auth}
  10 | paragraph | {Auth,Runbook}
  11 | heading   | {Auth}
  12 | paragraph | {Auth,Log}
(13 rows)

A heading is not inside itself: the ## Decisions heading at ord 2 has heading_path {Auth}, and its contents have {Auth,Decisions}.

What counts as heading text

One definition serves heading_path, #Heading anchors and append_to_section: the heading's concatenated plain inline text, with formatting markers dropped, wiki-links contributing their alias if they have one and their target otherwise, code spans contributing their literal text, any ^id marker stripped, then NFC-normalized and trimmed. It is what a reader of the rendered heading would type.

psql
SELECT ord, kind, heading_path, content
  FROM knowledge.blocks($md$## *Important* [[decisions|Decisions]]

Body.
$md$::markdown);
 ord |   kind    |      heading_path       |                content
-----+-----------+-------------------------+----------------------------------------
   0 | heading   | {}                      | ## *Important* [[decisions|Decisions]]
   1 | paragraph | {"Important Decisions"} | Body.
(2 rows)

Duplicate heading paths

heading_path is not unique. Two sibling headings with the same text are legal markdown, and pgmind stores them without complaint. Everything that addresses a section by heading path — read_section, append_to_section — takes the first match in document order and does not warn you that there was a second. This example writes a note and deletes it again:

The markdown dialect

pgmind parses CommonMark with exactly three GFM extensions enabled — tables, task lists, strikethrough — and then makes a second, deterministic pass over the result to find vault syntax: wiki-links, transclusions, tags and block-id markers. Autolinking, footnotes, superscript, description lists and smart punctuation are all off.

The precedence rule, before anything else

CommonMark inline parsing wins. Vault syntax is recognized only in the plain-text nodes that survive it, and never inside code spans, code blocks or HTML. The consequence people meet first: a link-reference definition anywhere in the document makes the matching [[…]] parse as a bracketed reference link, and no wiki-link is produced.

psql
SELECT kind, target FROM knowledge.links($md$A [[projects/auth]] link.
$md$::markdown);

SELECT kind, target FROM knowledge.links($md$A [[projects/auth]] link.

[projects/auth]: https://example.com/elsewhere
$md$::markdown);
   kind   |    target
----------+---------------
 wikilink | projects/auth
(1 row)

 kind | target
------+--------
(0 rows)

The second document produces no edge at all — not a dangling one. The definition turned the brackets into an ordinary reference link whose destination has a scheme, and a scheme-ful target is external. This is deterministic and golden-cased, and it is the price of not maintaining a private fork of CommonMark. If a note of yours mysteriously has no backlinks, grep it for ]:.

Wiki-links

A wiki-link is a closed grammar on a single line, inside [[ … ]]:

  • target — everything up to the first unescaped #, | or ]];
  • anchor — after the first unescaped #, up to the first unescaped | or ]]. Later # characters are part of the anchor text;
  • alias — everything after the first unescaped |, and it may contain #.
psql
SELECT kind, target, anchor, alias, block
  FROM knowledge.links($md$See [[projects/auth]], [[projects/auth#Decisions]],
[[projects/auth|the auth note]] and [[projects/auth#Decisions|why]].
$md$::markdown);
   kind   |    target     |  anchor   |     alias     | block
----------+---------------+-----------+---------------+-------
 wikilink | projects/auth |           |               |     0
 wikilink | projects/auth | Decisions |               |     0
 wikilink | projects/auth |           | the auth note |     0
 wikilink | projects/auth | Decisions | why           |     0
(4 rows)

Targets and anchors are whitespace-trimmed and NFC-normalized at extraction, so an NFD target typed on a Mac still matches its NFC-stored note. Aliases are trimmed but not normalized — they are display text. \#, \| and \] escape in all three parts. An anchor beginning with ^ makes the edge a blockref; a leading ! makes it a transclusion. And an empty target with no anchor — [[]], [[ ]], [[|alias]] — is not a wiki-link at all: the bracket pair is consumed and nothing is emitted.

psql
SELECT kind, target, anchor, alias
  FROM knowledge.links($md$Trimmed: [[  projects/auth  #  Decisions  |  why  ]].
Escaped: [[a\|b]] and [[c\#d]].
Block ref: [[projects/auth#^rotation]].
Not a link: [[]], [[ ]], [[|alias]].
Embedded: ![[projects/auth#Log]].
$md$::markdown);
     kind     |    target     |  anchor   | alias
--------------+---------------+-----------+-------
 wikilink     | projects/auth | Decisions | why
 wikilink     | a|b           |           |
 wikilink     | c#d           |           |
 blockref     | projects/auth | ^rotation |
 transclusion | projects/auth | Log       |
(5 rows)

Five rows for eight bracket pairs. The three empty-target forms produced nothing, which is the point: they are the shape a half-typed link has, and turning them into dangling edges would fill every vault with noise.

A transclusion is an edge, not an expansion. pgmind records that ![[projects/auth#Log]] points at that section; composing the target's text into the document is your query's job, and there is a recipe for it.

Wiki-links inside table cells

The GFM table extension splits cells on unescaped | before inline parsing runs. An aliased wiki-link in a cell is therefore two cells and no link. Escaping the pipe fixes it — the \| survives cell splitting and then behaves as the ordinary alias separator, which is what Obsidian does too:

psql
SELECT kind, target, alias FROM knowledge.links($md$| note | why |
|---|---|
| [[projects/auth|auth]] | one cell became two |
| [[projects/auth\|auth]] | escaped, so it survives |
$md$::markdown);
   kind   |    target     | alias
----------+---------------+-------
 wikilink | projects/auth | auth
(1 row)

One row from two rows of table. The surviving link is the escaped one. Note also that cell text is scanned as GFM-reconstructed content rather than raw source bytes, because cell source positions do not map back to the original — so a link found in a cell has no usable byte span.

Markdown links

An ordinary [text](target) is classified by its target. A target with a URL scheme is external and produces no vault edge. A scheme-less target is a candidate vault path: an optional #fragment is split off into the anchor first, then an optional .md suffix is stripped, then the result resolves like any other target and becomes an edge of kind mdlink. A pure-fragment link is a self-reference and is out of scope in v1.

psql
SELECT kind, target, anchor
  FROM knowledge.links($md$External: [docs](https://example.com/x) and [mail](mailto:a@b.c).
Internal: [runbook](runbooks/rotate-keys.md) and [sec](projects/auth#Decisions).
Fragment only: [here](#Decisions).
$md$::markdown);
  kind  |        target        |  anchor
--------+----------------------+-----------
 mdlink | runbooks/rotate-keys |
 mdlink | projects/auth        | Decisions
(2 rows)

Two of the five links produced edges. Since autolinking is off, a bare URL in the text is plain text and is never a link of any kind.

Tags

A tag is # followed by one or more characters from [A-Za-z0-9_/-], of which at least one must not be a digit. The # must be preceded by whitespace or by the start of the block's inline content in the original source — which is checked across inline-node boundaries, so **bold**#tag is not a tag even though the # begins a text node.

There is no collision with ATX headings: CommonMark requires a space after the # run for a heading, so a line-initial #tag is a paragraph containing a tag.

psql
SELECT tag, block
  FROM knowledge.tags($md$#architecture at block start, and mid-line #ops/on-call here.

**bold**#tag is not a tag, but **bold** #tag is. Nor is #123.

# A heading, not a tag

Hyphens-and_underscores: #v1-2_final.
$md$::markdown);
     tag      | block
--------------+-------
 architecture |     0
 ops/on-call  |     0
 tag          |     1
 v1-2_final   |     3
(4 rows)

Block 0 is the first paragraph, which starts with a tag; block 2 is the heading, which contributes nothing. #123 is rejected for being all digits — that rule exists so issue numbers and Markdown-style anchors do not become tags. Tags are stored exactly as written; the index matches them case-insensitively (see Sharp edges).

Block-id markers

A trailing  ^id — where id matches [A-Za-z0-9-]+ — pins a label onto a block. It is recognized at the end of the block's last content line, after container decoration is stripped and before trailing blank lines; for a setext heading, the content line is the one above the underline. Only heading, paragraph and list_item can carry one, and where a line is shared between nested eligible blocks the innermost block carries it.

psql
SELECT ord, kind, content, attrs->>'block_ref_id' AS block_ref_id
  FROM knowledge.blocks($md$# A heading ^h1

A paragraph. ^para

- an item ^item

```
code ^nope
```
$md$::markdown);
 ord |    kind    |   content    | block_ref_id
-----+------------+--------------+--------------
   0 | heading    | # A heading  | h1
   1 | paragraph  | A paragraph. | para
   2 | list_item  | an item      |
   3 | paragraph  | an item      | item
   4 | code_block | ```         +|
     |            | code ^nope  +|
     |            | ```          |
(5 rows)

Three things happened there. The marker is stripped from content, so adding one never changes a block's hash — that is what makes it usable as a stable label. The list_item at ord 2 did not claim ^item; its inner paragraph did, because the paragraph is the innermost block whose last content line the marker sits on. And the code block kept ^nope as content: code_block, table, html_block and thematic_break cannot carry a marker in v1, which is an acknowledged gap — those are also the kinds where automatic identity matching is weakest, so they lack the escape hatch precisely where it would help most.

Not special in v1

Obsidian callouts (> [!note] is an ordinary blockquote), comments (%%…%%), inline queries and Dataview syntax are all plain content. pgmind implements a documented subset of the Obsidian dialect rather than chasing bug-compatibility with a tool that has no specification, and everything in that subset is pinned by a golden corpus.

Frontmatter

A leading --- … --- block containing a YAML mapping becomes the note's properties (jsonb). It is part of the preamble, not a block, so it has no id, no hash and no history of its own beyond the note's.

Two keys are reserved. tags — a string or a list — is merged into the tag index at note level, with a NULL block. pgmind-pin is a boolean reserved for the context assembler that has not shipped yet; today it is stored and otherwise ignored.

psql
SELECT knowledge.properties($md$---
title: Auth
tags: [architecture, active]
pgmind-pin: true
owner: platform
---

# Auth
$md$::markdown);

SELECT tag, block FROM knowledge.tags($md$---
tags: [architecture, active]
---

# Auth #inline
$md$::markdown);
                                   properties
------------------------------------------------------------------------------

(1 row)

     tag      | block
--------------+-------

(3 rows)

Invalid YAML is never an error. A malformed or non-mapping frontmatter block is treated as ordinary CommonMark content — which is what Obsidian does, and what makes importing somebody else's vault survivable. It does mean the content parses as whatever those characters happen to be:

psql
SELECT ord, kind, content FROM knowledge.blocks($md$---
title: [unclosed
---

# Auth
$md$::markdown);
 ord |      kind      |     content
-----+----------------+------------------
   0 | thematic_break | ---
   1 | heading        | title: [unclosed+
     |                | ---
   2 | heading        | # Auth
(3 rows)

The opening --- became a thematic break and the next two lines became a setext heading. knowledge.properties() on that document returns {}. If a note's properties are unexpectedly empty, its frontmatter did not parse.

What survives into properties is what the YAML loader has already resolved by the time pgmind sees it, so several constructs people expect to be rejected are not. Anchors and aliases resolve: b: *v stores the anchored value. A tag is dropped and its scalar kept, so !!str 1 and !mytag 1 both store the string "1". A merge key is not merged — << is stored as an ordinary key holding the aliased mapping. What does count as invalid, and therefore as content, is a top-level sequence or scalar, a mapping with a non-string key, an alias with no anchor, and an empty block. A second YAML document never arises: the frontmatter ends at the first line that is exactly ---, so anything after it is markdown.

psql
SELECT knowledge.properties($md$---
a: &v 1
b: *v
n: !!str 1
---
$md$::markdown) AS resolved,
       knowledge.properties($md$---
c: *nope
---
$md$::markdown) AS rejected;
          resolved          | rejected
----------------------------+----------
 {"a": 1, "b": 1, "n": "1"} | {}
(1 row)

The content hash

Every block carries content_hash: BLAKE3 over the block's kind tag, a zero byte, and its normalized logical content. Normalization is exactly seven steps, and nothing else:

  1. start from the block's source span;
  2. strip enclosing container decoration the way CommonMark strips it — > prefixes, list-item markers, continuation indentation (the marker's style lives in attrs, not in content);
  3. for a list_item, exclude container children and their descendants: an item's content is its own direct non-container children;
  4. strip a trailing ^id marker together with the whitespace before it, searching content lines bottom-up;
  5. normalize CRLF and CR line endings to LF;
  6. apply Unicode NFC — including inside code blocks, which is a deliberate exception to “code is untouched”: it affects the hash only, never the stored bytes;
  7. strip trailing newline runs.

Trailing spaces are kept, because two of them are a CommonMark hard break and therefore semantic. Nothing else is collapsed, lowercased or reordered.

Steps 2 and 3 are what make the hash useful. The same sentence hashes the same whether it sits at top level, inside a quote, or three list levels deep:

psql
SELECT 'quoted' AS source, encode(content_hash, 'hex') AS content_hash
  FROM knowledge.blocks($md$> foo$md$::markdown)
UNION ALL
SELECT 'plain', encode(content_hash, 'hex')
  FROM knowledge.blocks($md$foo$md$::markdown);
 source |                           content_hash
--------+------------------------------------------------------------------
 quoted | 13a4c35e980e4b98f3026ef55f9b5e59559efe9710cf5ae2c784c97b46f20780
 plain  | 13a4c35e980e4b98f3026ef55f9b5e59559efe9710cf5ae2c784c97b46f20780
(2 rows)

What that buys is concrete. When you indent a paragraph into a list, or pull it out of a blockquote, or move it into a deeper sub-item, its hash does not move — so the write path's exact-match pass carries its block id, its citations keep resolving, and an embedding keyed on the hash is not recomputed. Without container invariance, reformatting a document would look like rewriting it.

The same reasoning gives three more invariants, and one deliberate non-invariant:

psql
SELECT (SELECT content_hash FROM knowledge.blocks($md$- foo$md$::markdown)
          WHERE kind = 'paragraph')
     = (SELECT content_hash FROM knowledge.blocks($md$foo$md$::markdown))
       AS list_invariant,
       (SELECT content_hash FROM knowledge.blocks($md$foo ^x$md$::markdown))
     = (SELECT content_hash FROM knowledge.blocks($md$foo$md$::markdown))
       AS marker_invariant,
       (SELECT content_hash FROM knowledge.blocks($md$# foo$md$::markdown))
     = (SELECT content_hash FROM knowledge.blocks($md$foo$md$::markdown))
       AS kind_matters;
 list_invariant | marker_invariant | kind_matters
----------------+------------------+--------------
 t              | t                | f
(1 row)

kind_matters is false because the kind tag is hashed in: a heading and a paragraph with the same words are different content.

What the hash is not

The hash answers did this change? It does not answer is this the same block? Two identical paragraphs are two blocks with one hash; one edited paragraph is one block with two hashes. Using a content hash as an identity is the mistake this whole design exists to avoid — see below.

Identity

A block id is a UUIDv7, minted by the extension at the moment a write creates the block. Never by the parser, never by the client, never gen_random_uuid() in SQL. Ids are opaque: the v7 time prefix exists to keep the primary-key index append-friendly, and you must not read anything out of it. Order comes from ord, time from revisions.

The invariant, in one sentence, and it has two halves:

  • Two blocks with identical content are still two blocks — same hash, different ids.
  • One block whose content changes is still one block — same id, different hash.

The first half, written and then cleaned up:

SELECT knowledge.write('notes/twins', $md$# Twins

Same words.

Id, hash and ^id label

Three different things, routinely confused:

Answers Who sets itStable across
block_idis this the same block? the extension, on write edits, moves, section renames, note renames
content_hashdid the content change? the parser, from the bytes container nesting, quoting, ^id markers, CRLF
block_ref_id (^id) what does the text call this block? whoever typed it nothing — it is editable text like any other

The ^id marker is a label, never an identity. It can be duplicated, deleted or moved to another block, and each of those is honoured exactly as written (ties break by document order). It does two jobs: it resolves #^id anchors, and it lets a whole-note rewrite assert “this block is that block” without pgmind having to guess. Conflating it with identity would hand id minting to whoever types in an editor.

The seeded note shows both the label and the kind-in-hash rule at once. ord 5 is a list item and ord 6 is the paragraph inside it — the same words, two blocks, two hashes, and the marker on the inner one:

psql
SELECT ord, kind, block_ref_id, left(encode(content_hash,'hex'), 12) AS hash, content
  FROM knowledge.blocks('projects/auth') WHERE ord IN (5, 6) ORDER BY ord;
 ord |   kind    | block_ref_id |     hash     |                  content
-----+-----------+--------------+--------------+-------------------------------------------
   5 | list_item |              | d7b89e8d6858 | Refresh tokens rotate every 24h #decision
   6 | paragraph | rotation     | 5b67c1e4e458 | Refresh tokens rotate every 24h #decision
(2 rows)

An anchor such as [[projects/auth#^rotation]] therefore resolves to the paragraph, not the item. After a split_block the id goes to the first fragment while the marker goes wherever your fragment text puts it, so the two can diverge — lawfully, and recorded in the revision's provenance. Internals has the full carry rules.

Link resolution

Every link is a row whether or not it points anywhere. Resolution runs at write time and is recomputed incrementally when a note is created or renamed. The rules, in order:

  1. the target is whitespace-trimmed and NFC-normalized;
  2. if it fails the path grammar, the edge is dangling with reason = 'invalid';
  3. exact path match against a live note in this vault;
  4. otherwise, if the target contains no /: a unique live note with that basename. More than one candidate is dangling with reason = 'ambiguous';
  5. otherwise dangling with reason = 'missing'. The target text is preserved either way.
psql
SELECT kind, target, resolved_path, dangling_reason
  FROM knowledge.links('notes/scratch') ORDER BY target;
   kind   | target  | resolved_path | dangling_reason
----------+---------+---------------+-----------------
 wikilink | auth    | projects/auth |
 wikilink | nowhere |               | missing
(2 rows)

[[auth]] resolved by basename because exactly one live note ends in that segment. Create a second one and the link becomes ambiguous — without anyone editing notes/scratch. That is edge repair on creation doing its job:

psql
SELECT knowledge.write('archive/auth', $md$# Archived auth

An unparseable target: [[/bad/]].
$md$);

SELECT target, resolved_path, dangling_reason
  FROM knowledge.links('notes/scratch') ORDER BY target;

SELECT target, resolved_path, dangling_reason FROM knowledge.links('archive/auth');
 target  | resolved_path | dangling_reason
---------+---------------+-----------------
 auth    |               | ambiguous
 nowhere |               | missing
(2 rows)

 target | resolved_path | dangling_reason
--------+---------------+-----------------
 /bad/  |               | invalid
(1 row)

Renaming the newcomer repairs the ambiguity, again without touching the linking note. This restores the demo vault:

psql
SELECT knowledge.move_note('archive/auth', 'archive/legacy-auth');

  FROM knowledge.links('notes/scratch') ORDER BY target;

 target  | resolved_path | dangling_reason
---------+---------------+-----------------
 auth    | projects/auth |
 nowhere |               | missing
(2 rows)
Deletion does not repair

Repair runs on note creation and rename. It does not run on delete_note: if you delete one of two ambiguous candidates, the ambiguous edges stay ambiguous until something else touches them. Rewriting or renaming the linking note re-resolves its edges. This is measured behaviour, not an inference.

Anchors are different from targets: they are stored as text and resolved at query time, not at write time. #Heading matches heading text (the normalized definition) first in document order; #^id matches block_ref_id. A link whose note resolves but whose anchor does not is not dangling — dangling_reason is about the note.

Revisions

A write that changes the note's bytes appends a revision row and swaps the note's head_revision. Revisions are per-note, numbered by seq from zero, and never deleted.

A byte-identical write records nothing

knowledge.write compares the incoming source against the stored preamble and tiles before parsing anything. If they match byte for byte it returns the current head and appends no revision, so re-sending the same document does not pad the history. expected_head is still checked before that comparison: a stale writer whose rewrite happens to be a no-op gets PM009, not a silent success. CAS answers “did you see what you were changing?”; the short-circuit only answers “did anything change?”.

psql
SELECT seq, verb, author, source, blocks_changed, reconstructable
  FROM knowledge.history('projects/auth');
 seq |     verb     | author | source | blocks_changed | reconstructable
-----+--------------+--------+--------+----------------+-----------------
   1 | update_block | amin   | api    |              1 | t
   0 | write        | amin   | api    |             13 | t
(2 rows)
ColumnMeans
seq per-note counter from 0. Usable directly as a time-travel argument: read_as_of(path, 0::bigint).
verb which operation wrote it. append_to_section records insert_blocks, because it resolves the anchor and then delegates.
author the writer's own claim, from the pgmind.author GUC; current_user when the GUC is unset. It is never verified — see below.
source 'api' for every shipped operation. 'sync' and 'rebind' are reserved for the file bridge and the rebinder.
blocks_changed how many block-level effects this revision recorded.
reconstructable whether this revision can still be reconstructed. It is exactly seq ≥ the note's history floor, and nothing else makes it false. Only pgmind.retain raises that floor; pgmind.excise redacts payloads in place and leaves it alone, so an excised revision still reads as reconstructable and reconstructs with a redaction marker where the erased text was.

pgmind.author is a plain string, capped at 200 characters (PM017 above that). Any session that can write can claim any author. Dressing that up — a registry, a required prefix, a foreign key to a principals table — would make an unverified claim look verified, which is worse than a string. Treat it as a label for your own audit trail, and put real authorization in grants and RLS.

psql
SET pgmind.author = 'agent:indexer';

SELECT knowledge.write('daily/2026-08-06', $md$# 2026-08-06

## Log

Reviewed the rotation window with [[people/ada]]. #decision

Rotated the signing key. #decision
$md$);

RESET pgmind.author;

SELECT seq, verb, author, source, blocks_changed
  FROM knowledge.history('daily/2026-08-06');
 seq | verb  |    author     | source | blocks_changed
-----+-------+---------------+--------+----------------
   1 | write | agent:indexer | api    |              1
   0 | write | amin          | api    |              3
(2 rows)

knowledge.blame() answers the per-block version of the same question, and adds two columns worth knowing about. confidence is NULL when the block's identity was carried deterministically — by an exact hash match, by an ^id claim, or by an explicit block operation — and carries a score between 0 and 1 when it was inferred by the rebinder. history_floor is the oldest seq still reconstructable for this note.

psql
SELECT ord, author, source, confidence, history_floor
  FROM knowledge.blame('projects/auth') WHERE ord IN (11, 12) ORDER BY ord;

-----+--------+--------+------------+---------------
  11 | amin   | api    |            |             0
  12 | amin   | api    |            |             0
(2 rows)

Time travel reads a note, or its blocks, as of a revision id, a seq, or (for read_as_of only) a timestamp. Block ids are stable across time, which is what makes a citation of the form path#block @ revision resolvable years later:

  FROM knowledge.blocks_as_of('projects/auth', 0::bigint) WHERE ord = 12;

SELECT change, before, after
  FROM knowledge.diff('projects/auth',
         (SELECT revision FROM knowledge.history('projects/auth') WHERE seq = 0),
         (SELECT revision FROM knowledge.history('projects/auth') WHERE seq = 1));

(1 row)

Same id at seq 0 as at head, different content. History is stored as pre-images rather than snapshots, so old revisions cost roughly a fifth of current state rather than a copy of it; the reconstruction algorithm and the frame cadence are in Internals.

The GUC scopes; it does not defend

SET pgmind.vault_id is USERSET. Any session that can run SQL can set it to any value and read that tenant's notes. The actual boundary is pgmind.enable_vault_rls() plus the grants you give your application role; the GUC then selects which policy-permitted vault you are working in. In a connection pool use SET LOCAL inside the transaction, or the next borrower inherits your tenant. Recipes.

A malformed pgmind.vault_id is PM001, not a silent fallback to the nil uuid.

The GUCs do not exist until the library loads

In a fresh session SHOW pgmind.frame_every fails with unrecognized configuration parameter. Call any pgmind function first — or LOAD 'pgmind'; — and all four settings (vault_id, author, frame_every, max_document_bytes) appear. SET works before the load, because PostgreSQL accepts a placeholder, and the value is honoured once the library initializes.

Errors

pgmind raises errors in SQLSTATE class PM. Every one carries a message, and a DETAIL line naming the condition and the offending value. Agents are expected to repair by re-reading, never by forcing.

CodeCondition Raised whenWhat to do
PM001pgmind_invalid_path a path fails the grammar after normalization; also a bad notes() glob or a malformed pgmind.vault_id run pgmind.path_normalize, check with pgmind.path_is_valid, retry
PM002pgmind_note_not_found no live note at that path in this vault check the path and the vault GUC; create the note. Reads of a syntactically invalid path report this rather than PM001
PM003pgmind_block_not_found block uuid absent, in another vault, or a merge keep outside the set re-read knowledge.blocks(); ids do not survive their note
PM004pgmind_fragment_arity the fragment parsed to the wrong number of top-level blocks update_block and merge_blocks want exactly one; split_block wants two or more
PM005pgmind_invalid_anchor before and after both given, or the anchor is not a legal v1 position give one or neither — neither appends after the last top-level block
PM006pgmind_container_constraint a v1 structural limit: non-contiguous merge set, cross-container move, container children in a fragment restructure the edit, or rewrite the note with write()
PM007pgmind_section_not_found the heading path matched nothing read the real heading paths from knowledge.blocks()
PM008pgmind_splice_restructures the spliced note re-parses differently outside the fragment — an unclosed fence or HTML block swallowing its neighbours close the construct in the fragment, or rewrite the note
PM009pgmind_stale_head expected_head is not the note's current head, or there is no live note to compare against re-read, re-derive the edit, retry. This is the ordinary optimistic-concurrency outcome
PM010pgmind_unknown_revision that revision uuid is not this note's a client bug — check where the id came from
PM011pgmind_history_unavailable the revision is below the retention floor, or no revision exists at or before that time nothing: the data was retained or excised away. Opposite meaning to PM010
PM012pgmind_excision_refused the excision target is still live at head pass and_head => true, or remove the content first
PM013pgmind_excision_incomplete in-transaction verification found residue after erasing nothing to retry — the transaction aborted and erased nothing. Report it
PM014pgmind_note_tombstoned the note was deleted by a concurrent transaction re-read; undelete_note if you want it back
PM015pgmind_path_taken a live note already occupies the destination path pick another path, or delete the occupant first
PM016pgmind_stale_block expected_hash is not the block's current content hash re-read the block. Unlike PM009 this fires only when your block changed
PM017pgmind_invalid_author pgmind.author is longer than 200 characters shorten it
PM018pgmind_vault_not_found no vault has that name or id check knowledge.vaults(), or create it. An unregistered id is an error, not a new empty vault
PM019pgmind_batch_arity a write_many batch has mismatched arrays, a NULL element, or more than 1000 notes fix the arrays — the DETAIL names the element index

Here is what four of them actually look like. Every PM error arrives with the same CONTEXT line, because custom SQLSTATEs are raised through a plpgsql helper; it is shown once and elided afterwards.

psql
SELECT knowledge.write('/bad/', $md$# x$md$);
ERROR:  pgmind: invalid note path
DETAIL:  pgmind_invalid_path — path "/bad/"
CONTEXT:  PL/pgSQL function pgmind.raise_error(text,text,text) line 3 at RAISE
SQL statement "SELECT pgmind.raise_error($1, $2, $3)"
psql
SELECT knowledge.read('/bad/');
SELECT knowledge.read_section('projects/auth', ARRAY['Nope']);
ERROR:  pgmind: note not found

Note the first one: reading a path that could never be legal reports not found, not invalid. The read path looks the note up rather than validating first, so PM001 is a write-side answer.

psql
SELECT knowledge.write('projects/auth', $md$# Auth$md$,
       expected_head => '00000000-0000-0000-0000-000000000000');

Catch them the way you catch any SQLSTATE — WHEN sqlstate 'PM009' in plpgsql, or by reading e.sqlstate in a client library. pgmind never raises a serialization failure (40001) and never retries internally; the retry policy is yours.

Sharp edges

Everything here is real, reachable from SQL, and surprises people. The operational traps — the double-evaluation trap, appending to a list-terminated section, concurrent writers — live in the cookbook. These are the ones about meaning.

heading_path is not unique

Two sibling headings may share text. read_section and append_to_section take the first match in document order, silently. Shown above.

Paths are case-sensitive, and NFC

Projects/Auth and projects/auth are two notes, and a glob for one will not match the other. Meanwhile a path typed in NFD is normalized on write but rejected by path_is_valid as given — the two functions do different jobs on purpose. Shown above.

notes().title is the basename

It is the path's last segment, not the frontmatter title. The frontmatter value is in properties, where you can query it with the rest of them:

psql
SELECT path, title, properties->>'title' AS frontmatter_title
  FROM knowledge.notes('projects/*');
     path      | title | frontmatter_title
---------------+-------+-------------------
 projects/auth | auth  | Auth
(1 row)

Tags group case-insensitively

Tags are stored exactly as typed, but the index groups by lower(tag) and reports the lexicographically smallest spelling. #Decision and #decision are one row in knowledge.tags(), and tagged() matches either spelling from either query:

psql
SELECT path, tag FROM knowledge.tagged('DECISION');

SELECT tag, notes, blocks FROM knowledge.tags();
       path       |   tag
------------------+----------
 daily/2026-08-06 | decision
 daily/2026-08-06 | decision
 projects/auth    | decision
 rfc/auth-01      | decision
(4 rows)

     tag      | notes | blocks
--------------+-------+--------
 active       |     1 |      0
 architecture |     2 |      2
 decision     |     3 |      4
 person       |     1 |      1
 runbook      |     1 |      0
(5 rows)

blocks is zero for active and runbook because those came from frontmatter: a note-level tag has no block. So notes and blocks are not two views of the same number, and neither of them is stats().tags, which counts raw tag rows — 10 by this point in the page, the 7 block-level rows above plus 3 note-level ones, for 5 distinct tags.

orphans() ignores self-links and dangling edges

An orphan is a live note with no inbound edge from another note. Linking to yourself does not rescue you, and being the target of a dangling link does not either, since a dangling edge resolves to no note at all. In the demo vault only the hub is an orphan — it links to everything and nothing links back to it:

psql
SELECT * FROM knowledge.orphans();

(1 row)

A whole-note rewrite runs the rebinder

Block operations assert identity: update_block keeps the id because you said so. write() cannot be told, so it works the identity out. Two deterministic passes run first — ^id claims, then exact-hash matches within the same section and then anywhere — and whatever they cannot match is handed to a similarity aligner, which carries ids with a confidence score instead of certainty.

This example rewrites the whole of projects/auth with one sentence changed. The paragraph's id survives, with a score:

psql
SELECT knowledge.write('projects/auth', $md$---
title: Auth
tags: [architecture, active]
owner: platform
---

# Auth

The service that issues and rotates credentials. Owned by [[people/ada]].

## Decisions

- [[oauth2]] over server sessions, see [[rfc/auth-01]] #architecture
- Refresh tokens rotate every 24h #decision ^rotation
- Access tokens live 15 minutes, no exceptions

## Runbook

Key rotation is [[runbooks/rotate-keys|documented separately]].

## Log

Rotated the signing key and the refresh secret.
$md$);

SELECT b.block_id, bl.confidence, left(encode(b.content_hash,'hex'), 12) AS hash
  FROM knowledge.blocks('projects/auth') b
  JOIN knowledge.blame('projects/auth') bl USING (block_id)
 WHERE b.heading_path = ARRAY['Auth','Log'];
               block_id               | confidence |     hash
--------------------------------------+------------+--------------
 019fd630-bc5a-…                      |  0.5833333 | 089cc9ae1e3c
(1 row)

Same id as the block in Identity — carried, not minted — with a new hash and a confidence of 0.58. Measured over the published edit corpus the aligner recovers 19 of 23 inferred bindings at recall 0.951 and precision 0.980, and it produces no mis-binding of its own beyond one genuinely undecidable duplicate case (rebinding-v2). That is good, and it is not a guarantee. If a block's identity must survive an external round trip, give it an ^id marker or edit it with a block operation; those two are deterministic, and everything else is a score you can read in blame().
