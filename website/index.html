Markdown won. Then it hit a server.

The complicated ideas came first. What agents actually run on is a folder of markdown: memory files, Obsidian vaults, a docs/ tree piped into a prompt. It won because models read and write it natively, humans can still edit it, and there is no schema to argue about.

On a laptop that is the whole story: one user, one writer, one disk. Then the agent moves into a backend, and the same folder starts to break.

  • Two requests write the same note. One wins, silently.
  • “What links here?” is a grep across the tree, on every call.
  • History means shelling out to git inside a request handler.
  • Every tenant needs its own tree, and every read has to prove it stayed there.
  • Notes on disk, vectors in a service, no transaction across the two.
  • Backup and migration become a second system beside the database you already run.

None of that is markdown’s fault. It is the filesystem’s.

So keep the markdown. Replace the filesystem.

pgmind is a PostgreSQL extension. Same notes, same wiki-links, same tags, kept as rows instead of files. The list above answered, and a few things a folder was never going to do:

  • No lost writes. If the note changed since you read it, your save fails instead of quietly overwriting someone else.
  • Everything is queryable. Every heading, paragraph, link and tag is a row. An outline, one section, or “what links here?” is a single query.
  • Nothing is overwritten. Each edit adds a version, so you can see what changed, who changed it, and read the note as it was last week.
  • Every paragraph has an ID. An agent can point at the exact paragraph it used, and that pointer still works after the note is edited.
  • Multi-tenant out of the box. Tag each vault with a tenant ID, and Postgres row security keeps every query inside it.
  • You can really delete. History is kept by default, but erasing something is a real, logged operation, not a workaround.
  • It is just your database. Notes, indexes and any embeddings you add all live in Postgres, inside the backup you already take.
  • Easy in, easy out. pgmind import ./vault brings a markdown folder in. pgmind export ./vault gives it back, unchanged.

The API is SQL

One public schema, knowledge, and the nouns a vault already has: notes, sections, blocks, links, tags. Markdown goes in, the same bytes come out. 

-- Save a note. $1 is the version you last read.
-- If someone else saved in between, this errors instead of overwriting them.
SELECT knowledge.write('projects/auth', $md$
# Auth

## Decisions
- [[oauth2]] over server sessions, see [[rfc/auth-01]] #architecture
$md$, expected_head => $1);

-- ERROR:  pgmind: head moved, re-read and retry


-- Add one line under a heading, without reading or rewriting the note.
SELECT knowledge.append_to_section(
    'projects/auth',
    ARRAY['Auth','Decisions'],
    $md$- Rotate refresh tokens every 24h #decision$md$
);

In main There are finer-grained edits too (update_block, move_block, split_block, merge_blocks), so two agents working on different paragraphs of the same note never collide.

-- Table of contents. Headings are already rows, so nothing is re-read.
SELECT attrs->>'level' AS level, attrs->>'text' AS heading
FROM   knowledge.blocks('projects/auth')
WHERE  kind = 'heading';

-- Then read back just one section
SELECT knowledge.read_section('projects/auth', ARRAY['Auth','Decisions']);

-- What links to this note, and from which paragraph
SELECT src_path, kind, excerpt
FROM   knowledge.backlinks('projects/auth');

-- Everything tagged #architecture
SELECT path FROM knowledge.tagged('architecture');

-- Notes nothing links to
SELECT path FROM knowledge.orphans();

In main Headings, links and tags are worked out once, when the note is saved. So an outline is just a lookup, and an agent can read the map before asking for the part it actually needs.

-- Every version of a note, newest first
SELECT seq, author, verb, created_at
FROM   knowledge.history('projects/auth');

-- What changed between two versions, paragraph by paragraph
SELECT change, before, after
FROM   knowledge.diff('projects/auth', $1, $2);

-- Who last touched each paragraph
SELECT ord, author, changed_at
FROM   knowledge.blame('projects/auth');

-- The note as it looked a week ago
SELECT knowledge.read_as_of('projects/auth', now() - interval '7 days');

In main Versions are stored as deltas, so keeping all of them is cheap. source tells you whether a change came from your app or from a folder sync, and blame is honest about the rare cases where a paragraph was matched up by guesswork rather than tracked.

-- The note, what it pulls in, and what it links to. Packed to a token
-- budget, with a reference on every paragraph it includes.
SELECT knowledge.context(root => 'projects/auth', token_budget => 12000);


-- It is an ordinary SQL function, so it works with your own tables.
-- Keep everything inside one tenant:
SET LOCAL app.tenant_id = $1;

-- ...then let your tables choose what gets pinned into the budget:
SELECT knowledge.context(
    root         => 'projects/auth',
    token_budget => 12000,
    pins         => ARRAY(
        SELECT n.path
        FROM   knowledge.notes('runbooks/**') n
        JOIN   incident i ON i.runbook = n.path
        WHERE  i.customer_id = $2 AND i.status = 'open'
    )
);

-- Same notes and same arguments always give the same output. No model
-- is called here, and nothing leaves the database.

Phase 5 · 0.1.0 Postgres row security applies here like anywhere else, so one policy keeps every tenant inside its own vault. The smaller pieces context uses (search, traverse, backlinks) stay callable on their own, and context_explain shows exactly what went in, what got cut, and why.

-- The agent answers with a reference instead of a vague "from the docs":
--     projects/auth#^k3f9
-- Below, $1 is that paragraph id and $2 the version it read.

-- What the paragraph said at the moment the agent read it
SELECT heading_path, content
FROM   knowledge.blocks_as_of('projects/auth', $2)
WHERE  block_id = $1;

-- Where it sits in the note today, so your UI can scroll to it
SELECT heading_path, span_start, span_end
FROM   knowledge.blocks('projects/auth')
WHERE  block_id = $1;

-- And who put it there
SELECT author, source, changed_at
FROM   knowledge.blame('projects/auth')
WHERE  block_id = $1;

In main A paragraph keeps its id across edits and old versions are never thrown away, so a reference from last month still points at what the agent actually read, not at whatever that paragraph says today. context will emit these references inline in 0.1.0; the lookups above work now.

Where it fits

What the roadmap is measured against, end to end. A phase that serves none of these does not ship.

One vault, many agents

Many agent instances, one knowledge base, all writing at the same time without coordinating.

Filesystem memory, server-side

Your agent memory is a folder of files. It works until that folder has to serve thousands of accounts.

Obsidian, not local

One team vault: humans edit it in their own editor, agents read it in production.

Knowledge you can join

The answer depends on the asker: their tenant, their plan, their open incidents. Same database, one query.

Answers you can audit

“The agent said so” is not good enough. Every claim points back to the paragraph behind it.

Forgetting, on purpose

A right-to-be-forgotten request lands, and the old revisions have to go too.

And where it does not fit: one writer, one machine, offline. That case should stay on files. The handbook’s risk table says so too.

Get started

Rust is pinned by rust-toolchain.toml, so rustup installs the right one. On macOS you also need brew install pkgconf icu4c. 

git clone https://github.com/MarosiLabs/pgmind
cd pgmind

make setup   # cargo-pgrx + a pgrx-managed Postgres
make build   # PG=18 by default; make build PG=16
make test    # runs inside a real Postgres

Then the manual takes it from there: a quick start, the vault model, how the storage and version engine actually work, a complete SQL reference, and a cookbook.

Behind it, the design documents have a precedence order: the handbook holds the architecture laws, the product plan is the operating blueprint, an RFC decides each phase before it is implemented, and the audit is the evidence the whole thing was argued against.
